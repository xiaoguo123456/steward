# recipes

只读的菜谱内容。

## 它为什么不受 RLS 约束

菜谱是平台提供的内容，不是用户数据：所有人看到同一份。因此 `recipes` 表
不带 `user_id`，不启用行级安全，也没有面向用户的写接口——写入只由
`cmd/seed` 完成。

用户自己的东西是**本周菜单**和**实际摄入**，它们分别是 Note/Task 与 Record，
仍然在各自的用户表里，照常受 RLS 约束。这条边界要守住：一旦把「谁收藏了
哪道菜」塞进这张表，它就变成用户数据了，所有隔离规则都得重来。

## 来源与授权是必填的

`source_name`、`license` 与 `content_version` 是 NOT NULL，`image_url` 上还有
一条约束：没有 `image_credit` 就不许挂图。

这不是形式主义。不知道一条内容从哪来、按什么授权展示，就等于不知道自己
有没有权利展示它；等到内容已经上线再补，成本会高得多。

当前库里是 6 条平台自有的占位内容，`image_url` 全部为空 —— 与其挂一张来路
不明的图，不如先没有图。正式菜谱接入前必须逐条确定来源、作者、图片权利与
授权范围。

## 过敏原是硬过滤

`exclude_allergens` 在 SQL 里直接排除，不是排序权重：

```sql
AND NOT (allergens && sqlc.arg(exclude_allergens)::text[])
```

任何推荐、排序或个性化都不得让一条含过敏原的菜谱重新出现。这条规则放在
查询里而不是应用层，就是为了让它没有被绕过的余地。

## 中文搜索

按菜名与食材搜索用 `pg_trgm` + `ILIKE`。Postgres 默认分词器不切分中文，
`to_tsvector` 会把整句当成一个 token，搜不到子串。
