# recipes

菜谱内容（只读、共享）与用户自己的食谱数据（饮食档案、收藏、做过、本周菜单）。

## 一张表不受 RLS，其余全都受

菜谱是平台提供的内容，不是用户数据：所有人看到同一份。因此 `recipes` 表
不带 `user_id`，不启用行级安全，也没有面向用户的写接口——写入只由
`cmd/seed` 完成。

**其余五张表都是用户数据**（见 `userdata.go` 与迁移 00016／00017）：
`recipe_diet_profiles`、`recipe_favorites`、`recipe_cook_logs`、
`meal_plans`、`meal_plan_entries`，每张都 ENABLE + FORCE 行级安全。

这条边界要守住：一旦把「谁收藏了哪道菜」塞进 `recipes` 表，
它就变成用户数据了，所有隔离规则都得重来。

## 几条不显然的规则

- **身体数据只能由用户自己填。** 不接受任何推断，能力层也没有登记对应的
  Capability。`diagnosed_condition` 同理——它为 true 时不生成治疗型菜单，
  并提示结合医生或营养师建议；这个产品不提供诊断、治疗承诺或用药建议。
- **菜单只存已确认的那版。** AI 生成的预览留在客户端，用户点过「采用」
  才走到 `ConfirmMealPlan`。整周一次性覆盖并推进版本号：
  逐格增量提交会让「这周到底是哪一版」说不清楚。
- **周起始日由服务端算**（`WeekStartFor`）。周一还是周日开始是用户偏好，
  「今天」是哪天取决于用户时区，客户端自己推必然和服务端不一致。
  条目按真实日期存，不用「周几」——跨周跨时区时「周三」并不唯一。
- **合并食材时份量并列而不是求和。**「2 个」加「少许」算不出准确总量，
  硬凑一个数反而误导。能不能相加是单位问题，不是字符串问题。
- **购物清单复用 TaskList / Task**，不新增同义的食材待办类型。
  每个用户只有一份活动购物清单；从菜单确认的食材合并进去，同名未完成商品合并份量。
  清单与全部条目在同一个事务里落库，失败时不留下空清单。

## 来源与授权是必填的

`source_name`、`license` 与 `content_version` 是 NOT NULL，`image_url` 上还有
一条约束：没有 `image_credit` 就不许挂图。

这不是形式主义。不知道一条内容从哪来、按什么授权展示，就等于不知道自己
有没有权利展示它；等到内容已经上线再补，成本会高得多。

当前测试与生产库使用已确认授权的懒饭内容，封面和步骤图只保存稳定对象键，
由服务端按当前分发方式生成 URL。后续接入其他来源时仍须逐条确定来源、作者、
图片权利与授权范围。

## 过敏原是硬过滤

`exclude_allergens` 在 SQL 里直接排除，不是排序权重：

```sql
AND NOT (allergens && sqlc.arg(exclude_allergens)::text[])
```

任何推荐、排序或个性化都不得让一条含过敏原的菜谱重新出现。这条规则放在
查询里而不是应用层，就是为了让它没有被绕过的余地。

## 中文搜索

按菜名与食材搜索用 `pg_trgm` + `ILIKE`。Postgres 默认分词器不切分中文，
`to_tsvector` 会把整句当成一个 token，搜不到子串。

## 发现分类

发现页按分类直接查询全库，不能先取前 100 条再由客户端筛选。`seasonal` 还会
按中国时间选择当前季节内部标签（`season_spring`、`season_summer`、
`season_autumn`、`season_winter`），所以只返回当前自然旺季的菜。四季边界固定为
春季 3—5 月、夏季 6—8 月、秋季 9—11 月、冬季 12—2 月。
减脂、增肌和健康控糖标签由导入工具的版本化确定性规则生成；线上请求不调用模型。

## 餐次映射

`meal_slots` 区分 `breakfast`、`lunch` 和 `dinner`，菜单查询会按餐次硬筛选。
它不是对来源标签的原样复制：导入工具会用确定性规则校验来源餐段，明显偏午晚餐的
咖喱类不会进入早餐自动菜单。原始分类仍保留在 `tags` 中供审计，用户也可以继续
浏览并手动加入这类菜谱。
