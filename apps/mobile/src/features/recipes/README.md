# 食谱前端原型模块

## 职责

- 为首页“食谱”入口提供本周菜单、菜谱发现、饮食问卷、菜谱详情、烹饪模式和购物确认的前端交互原型。
- 使用本地 Fixture 验证信息架构、状态和确认流程，不声明后端事实，不承担正式营养计算。
- 明确区分菜单中的“计划摄入”和用户确认记录后的“实际摄入”。

## 路由入口

- `features/recipes`：本周菜单与菜谱发现。
- `features/recipes/week`：整周菜单预览与采用确认。
- `features/recipes/questionnaire`：四步饮食问卷。
- `features/recipes/recipe/[id]`：菜谱详情。
- `features/recipes/cooking/[id]`：分步烹饪模式。
- `features/recipes/shopping`：由菜单生成购物清单前的确认页。

## 本地公开内容

- `model.ts`：仅供前端原型使用的展示类型。
- `mock-data.ts`：演示菜谱、周菜单、分类和问卷默认值。
- `recipe-context.tsx`：路由组内共享的非权威交互状态。
- `theme.ts`：复用 App 公共中性色，并限定食谱橙色的语义用途。
- `components/recipe-ui.tsx`：食谱场景的共享视觉组件。

## 视觉约束

- 页面背景、文字、分隔线、浅色表面和品牌绿必须复用 `theme/tokens.ts`，不得再创建一套“健康应用”色板。
- 橙色只用于餐次、步骤和食物类别等餐食语义；主要操作、选中态和成功状态继续使用 App 品牌绿。
- 菜谱内容以真实图片、白底、扁平列表和清晰文字层级建立辨识度，避免营养仪表盘、推荐算法面板和多层浅色卡片。

## 领域边界

- AI 只能提供候选菜单；采用菜单、加入某餐、生成购物清单和记录实际摄入都需要用户确认。
- 过敏原和明确禁忌属于确定性硬过滤条件，不能被 AI 排序覆盖。
- 正式收藏与个人补充说明复用 Note，正式购物清单复用 TaskList / Task；本模块不得新增同义业务实体。
- 正式接入外部菜谱前必须补充只读内容契约，并记录来源、作者、图片权利、授权范围和版本。
- 本地 `Recipe`、`WeekPlan` 等类型不得直接作为网络 DTO；网络字段仍以 `packages/contracts/openapi` 为唯一来源。
