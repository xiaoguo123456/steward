# 食谱模块

## 职责

- 为首页“食谱”入口提供本周菜单、菜谱发现、饮食问卷、菜谱详情、烹饪模式和购物确认。
- 菜单上的营养数字是**这份方案本身的能量**，不是用户的摄入。用户加不加餐、
  在外面吃了什么，我们不追踪；文案上不要写成“你的摄入”，也不要拿它去暗示。
  用户主动记录的实际摄入是 Record，走记录项接口，两者不混在一起展示。

## 数据来源

全部走契约接口，本地不留副本：

| 东西 | 接口 | 归属 |
|---|---|---|
| 菜谱内容 | `GET /v1/recipes` | 平台只读内容，所有人看到同一份 |
| 本周菜单 | `GET/PUT /v1/meal-plans` | 用户数据，受 RLS |
| 饮食档案 | `GET/PATCH /v1/me/diet-profile` | 用户数据，身体数据属高敏 |
| 收藏／做过 | `/v1/recipes/{id}/favorite`、`/cooked` | 用户数据 |
| 购物清单 | `/v1/meal-plans/shopping-draft` | 创建出来的是正式 TaskList / Task |

唯一留在本地的是**还没点「采用」的菜单草稿**：规格 8.2.2 要求预览只是预览，
所以草稿不落库——用户改到一半退出去，下次看到的应当仍是他上次确认过的那份。

本周从哪天开始由服务端算：周一还是周日开始是用户设置，客户端自己推会不一致。
菜单按真实日期存，不用「周几」。

合并购物食材也在服务端：客户端自己合并一遍，迟早和真正创建出来的清单对不上。

## 路由入口

- `features/recipes`：本周菜单与菜谱发现。
- `features/recipes/week`：整周菜单预览与采用确认。
- `features/recipes/questionnaire`：四步饮食问卷。
- `features/recipes/recipe/[id]`：菜谱详情。
- `features/recipes/cooking/[id]`：分步烹饪模式。
- `features/recipes/shopping`：由菜单生成购物清单前的确认页。

## 本地公开内容

- `model.ts`：仅供前端原型使用的展示类型。
- `category-options.ts`：发现页的分类文案。菜谱、菜单、档案与收藏都来自服务端，这里没有它们的本地副本。
- `recipe-context.tsx`：把上面几个数据层拼在一起，供路由组内共享。
- `theme.ts`：复用 App 公共中性色，并限定食谱橙色的语义用途。
- `components/recipe-ui.tsx`：食谱场景的共享视觉组件。

## 视觉约束

- 页面背景、文字、分隔线、浅色表面和品牌绿必须复用 `theme/tokens.ts`，不得再创建一套“健康应用”色板。
- 橙色只用于餐次、步骤和食物类别等餐食语义；主要操作、选中态、进度和成功状态统一使用首页的 `primary`，小字号绿色操作文字使用 `primaryStrong`。
- 分区标题统一使用首页的 16／23 Semibold 层级；白色画布、浅灰功能面与扁平列表承担主要分区，不用更深的“食谱专属”绿色制造独立皮肤。
- 本周首页的健康目标入口使用两层扁平状态行：当前目标采用正文强调字号，每日能量作为次级信息换行展示，档案操作不得降为说明文字大小；整行触控高度不小于 44，不额外包裹卡片。
- 菜谱内容以真实图片、白底、扁平列表和清晰文字层级建立辨识度，避免营养仪表盘、推荐算法面板和多层浅色卡片。
- 营养摘要使用单层浅中性底板和对齐建立分组，不用横纵分隔线拼成表格；早餐、午餐和晚餐分别使用“餐别标题＋换一道＋菜品行”的扁平区段，组内紧凑、组间留白，不重复包裹卡片。
- 说明文字只在影响当前填写、数据用途或安全后果时展示，不用“可随时修改”等无关安抚、产品能力声明或免责声明式文案填充常规页面；身体数据可以简明说明用途和修改方式，健康风险提示仅在用户声明相关病情或用药等风险条件后按场景出现。

## 领域边界

- AI 只能提供候选菜单；采用菜单、加入某餐、生成购物清单和记录实际摄入都需要用户确认。
- 过敏原和明确禁忌属于确定性硬过滤条件，不能被 AI 排序覆盖。
- 购物清单复用 TaskList / Task，不新增与之同义的食材待办类型。
- 正式接入外部菜谱前必须补充只读内容契约，并记录来源、作者、图片权利、授权范围和版本。
- 本地 `Recipe`、`WeekPlan` 等类型不得直接作为网络 DTO；网络字段仍以 `packages/contracts/openapi` 为唯一来源。
