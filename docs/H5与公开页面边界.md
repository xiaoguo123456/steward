本项目确实缺少可公开访问的《用户协议》《隐私政策》页面。代码中也尚未提供登录页真实链接、“我的”中的法律入口，以及无需安装 App 即可发起账号删除的 Web 路径。正式发布前这些项目属于上线阻塞项，不得用空白页、占位文案、PDF、失效链接或仅登录后可见的页面代替。

## 1. 总体决策

### 1.1 适合做成 H5 的内容

以下页面必须是公开、响应式、免登录的 H5，并保持稳定 URL：

| 页面 | 正式 URL | 主要用途 |
|---|---|---|
| 法律与支持首页 | `/legal` | 汇总全部法律文本、版本与联系入口 |
| 隐私政策 | `/legal/privacy` | App 内查看、应用商店隐私政策 URL、个人信息处理告知 |
| 用户协议 | `/legal/terms` | 登录注册前查看服务规则、责任边界与账号规则 |
| 个人信息收集清单 | `/legal/personal-information` | 按业务场景说明字段、目的、方式与保存期限 |
| 第三方信息共享清单 | `/legal/third-parties` | 列出短信、对象存储、AI、地图等实际接入方与处理范围 |
| 账号与数据删除 | `/legal/account-deletion` | 说明删除范围、处理时限，并在能力完成后允许 Web 发起删除请求 |
| 帮助与联系我们 | `/support` | 应用商店 Support URL、问题反馈和运营主体联系方式 |

测试环境使用 `https://test-steward.qhzhiyin.com`，正式环境使用 `https://steward.qhzhiyin.com`，路径保持一致。应用商店只能填写正式环境 URL。

### 1.2 为什么复用现有 Expo Web

`apps/mobile` 已使用 Expo Router `web.output=static`，生产流水线也已经构建并部署 `mobile-web`。Expo 静态导出支持把 `public` 内容复制到 `dist`，因此当前不新增独立 H5 仓库或单独部署服务：

- 纯内容法律页面放在 `apps/mobile/public/legal`，帮助页放在 `apps/mobile/public/support/index.html`，作为不需要 React 水合的静态 HTML。
- 页面不进入 App Root Provider，不依赖登录态、SecureStore、用户 API 或设备权限；关闭 JavaScript 后核心文本仍必须完整可读。
- 法律内容使用仓库内版本化源文件，页面展示“生效日期、当前版本、更新摘要和联系方式”。
- App 通过 `expo-web-browser` 或系统浏览器打开正式 URL，不引入 `react-native-webview`，不把远程页面伪装成本地原生页面。
- 法律文本部署后可独立于 App 发版更新；但重大变更仍要按适用规则在 App 内重新告知或重新取得同意，不能静默改网页。

若以后出现 Web 账号删除表单、大量营销内容、CMS、多语言 SEO 或独立运营团队，再评估拆分 `apps/public-web`，但保持既有 URL 不变。只有少量法律与帮助页面时提前拆站会增加镜像、域名、监控和发布链路，没有足够收益。

### 1.3 三层交付与更新策略

“减少每次都发布新版 App”是合理目标，但必须按变更依赖选择交付通道，不能把所有可远程更新的内容都等同于 H5：

| 交付层 | 适用变更 | 更新方式 | 明确边界 |
|---|---|---|---|
| H5 | 法律／帮助／活动等公开内容，以及读为主、轻交互、允许在线使用的功能 | Web 独立部署 | 不新增原生权限、后台能力或任意原生桥接；写操作仍走正式 API |
| React Native + OTA | 不改变原生运行时的 JavaScript、样式、文案、图片和小型缺陷修复 | 受控 OTA 渠道 | 已按 `ADR-028` 接入代码与发布门禁；只有配置 Expo Project／签名 Secret、发布包含验签证书的新原生包并完成回滚演练后，才能对该版本正式承诺 OTA |
| 应用商店原生版本 | 原生 SDK／依赖、权限、通知、后台任务、相机／麦克风／定位、原生容器和不兼容运行时变化 | App Store／应用商店发布 | 必须完成商店审核、权限申报、隐私清单和旧版本兼容检查 |

H5 部署、OTA 与 Feature Flag 都不能用来规避商店审核或在审核后静默改变产品的核心用途。涉及重大功能、隐私处理、订阅付费或审核申报的变化，即使技术上能远程下发，也要先完成对应产品、合规和商店评审。

### 1.4 H5 与原生判定

判断标准不是页面叫“内容页”还是“功能页”，也不是“开发快不快”，而是用户任务对状态、权限、离线和风险的要求。

功能同时满足以下条件时，优先评估 H5：

1. 以阅读、浏览、筛选或少量表单为主，重载页面不会破坏重要任务。
2. 断网时显示明确不可用提示可以接受，不要求可靠离线编辑或本地队列。
3. 不依赖相机、麦克风、定位、通知、后台任务、健康数据等原生能力。
4. 不承担登录安全、隐私控制、AI 写入确认或高风险／高频核心状态变更。
5. 频繁更新、公开分享、搜索索引、跨端复用或独立运营至少带来一项明确收益。

出现下列任一情况时默认保持原生：原生权限或生命周期、可靠离线、高频手势和即时状态、敏感数据控制、高风险写入、后台运行、系统级通知，以及核心“输入—理解—确认—执行”闭环。确需例外时必须在功能规格和架构 ADR 中说明收益、风险、降级与回退路径。

| 模块类型 | 默认载体 | 原因与边界 |
|---|---|---|
| 法律文本、第三方清单、个人信息清单、帮助中心 | H5 | 需要免登录、可分享、可被商店审核直接打开，内容更新不应强制发新版 App |
| 账号删除的公开说明 | H5 | 卸载 App 后仍能访问；不能只写“请重新安装 App” |
| 账号删除的身份验证与提交 | H5 + 正式 API | Web 端使用手机号验证码和单用途 reauth，复用 Auth／Retention Domain；不得在浏览器直接拼接数据库操作或手写平行 DTO |
| 活动规则、版本说明、公开 FAQ | 优先 H5 | 内容型、低交互、更新频繁；若需要登录态或写入用户数据，转入原生或正式 Web 应用流程 |
| 新功能介绍、模板／案例中心、使用教程 | 优先 H5 | 适合独立更新和分享；下载模板或创建正式 Object 时回到 App 并由用户确认 |
| 食谱发现、攻略、烹饪步骤 | 条件采用 H5 | 公开浏览与只读详情适合 H5；收藏、加入购物清单和个性化推荐仍回到原生并走正式契约 |
| 行程、笔记、周报、AI 报告的公开只读分享 | 条件采用 H5 | 只展示经过用户明确分享的最小数据；编辑、撤销分享、私有来源与 AI 建议确认保持原生 |
| 数据导出说明与下载状态 | 条件采用 H5 + 正式 API | 说明和一次性下载可以使用 Web；生成、鉴权、过期、撤销和审计由正式领域能力负责 |
| 首页、计划、任务、日历、笔记、打卡 | 原生 | 高频、强状态、离线恢复、手势和动态字号要求高，不因“页面多”改成 H5 |
| 首页“时光、音乐、灵感、心情”分区 | 原生 | 分别涉及媒体、音频生命周期与可能的后台播放、私人内容检索／来源控制和私密正文；心情日记第一阶段不提供公开分享。公开只读回忆以后可以单独评估 H5，权限、编辑、AI 确认和删除控制保持原生 |
| 亲友人物关系管理 | 原生 | 涉及私密人物资料、关系筛选与联系人选择；第一版优先手动添加，以后导入也优先使用系统联系人选择器按人授权，不默认申请整本通讯录。公开人物编辑、AI 确认和删除控制不得下放到 H5 |
| 任务创建／编辑、提醒时间、购物勾选、记账录入、运动计时 | 原生 | 属于高频即时写入或依赖通知、后台、定位与离线恢复，网络重载不能成为正常交互的一部分 |
| Capture、录音、拍照、图片选择、运动定位 | 原生 | 依赖权限、传感器、媒体草稿、中断恢复和原生生命周期 |
| 登录验证码、AI 候选确认、资料修改、手机号换绑、隐私控制 | 原生 | 涉及用户确认、敏感状态和本地会话；法律说明可以跳 H5，操作本身必须走正式原生流程 |
| 管理后台 | `apps/admin` Web | 面向内部运营，不嵌入移动端，也不与公开法律页面共用权限和导航 |

### 1.5 功能型 H5 的工程边界

当前只建设公开静态 H5，不在移动端散落任意 WebView。未来出现真实的登录态功能型 H5 需求时，必须先完成以下设计，再开始编码：

- 优先用系统浏览器或 `expo-web-browser` 承载公开、只读和可分享页面，并提供返回 App 的 Universal Link／App Link。
- 需要嵌入 App 时只能建设一个受审计的 H5 容器；新增容器本身属于原生能力，需要应用商店发版。容器固定 HTTPS 域名白名单，禁止任意跳转和默认开放相机、定位、文件、剪贴板等桥接。
- 登录态不得通过 URL、日志或页面脚本传递长期 Token。使用短时、单用途的会话交换码，服务端限制受众、来源、有效期和重放，并提供退出、撤销与会话失效能力。
- 网络数据继续以 `packages/contracts/openapi` 为唯一来源，Web 使用生成 Client 和运行时校验；服务端按当前用户隔离，写操作具备幂等、限流、版本冲突和审计。
- 必须覆盖首次加载、空、错误、离线、会话过期、页面刷新、取消和重复提交状态。H5 失败不得把用户误导为操作成功；核心任务必须有原生降级或明确的稍后重试路径。
- App 与 H5 按 capability 协商，不依赖“所有用户已经升级”的假设。下线页面时保留可理解的过期页和安全回到 App 的入口。

## 2. 登录、协议与隐私入口

- 登录页在首次发送验证码前展示未默认勾选的确认项：“我已阅读并同意《用户协议》和《隐私政策》”。两个标题分别打开对应 H5，返回后保留手机号和勾选状态。
- 未确认时不能发送验证码；读屏必须说明禁用原因。不能只在登录按钮下写“登录即同意”，因为手机号在请求验证码时已经开始处理。
- 服务协议确认不能替代图片、录音、精确位置、第三方 AI 等场景的单独告知或授权。媒体首次上传确认仍按现有设计独立出现。
- “我的”增加“法律与支持”分组，至少提供“隐私政策”“用户协议”“帮助与联系”；原始 Capture、自动删除、撤回同意、账号删除等实际控制继续放在原生“隐私与数据”。
- 页面链接加载失败时保留当前输入并提供“重试／复制链接／稍后查看”；不得因 H5 临时不可用把用户误标为已经同意。

## 3. 页面内容与版本要求

隐私政策至少覆盖：

- 个人信息处理者的名称和联系方式。
- 收集的数据、收集方式、使用目的、必要性与保存期限。
- 手机号、用户正文、图片、音频、位置、设备／诊断信息等实际数据类别。
- 短信、对象存储、地图、AI／OCR 等实际第三方处理者、处理目的、地区与保留方式。
- 用户查询、更正、复制、撤回同意、删除单项数据和删除账号的方式。
- 未成年人、跨境传输、安全事件、政策更新与申诉渠道。
- 与 App Store Privacy Details、Google Play Data safety 以及运行中第三方 SDK 的一致性。

用户协议至少覆盖：服务范围、账号规则、用户内容、AI 结果边界、禁止行为、服务变更／中断、知识产权、责任限制、终止、通知、适用法律与争议解决。正式文字必须由具备授权的产品／法务负责人确认，开发者不得根据接口字段自行生成一份“看起来完整”的协议。

每次发布法律文本必须：

1. 更新版本号、生效日期和变更摘要。
2. 保存可审计的旧版本，不让旧同意记录失去对应文本。
3. 检查 App 内链接、应用商店 URL、个人信息清单、第三方清单和商店数据申报是否一致。
4. 判断是否需要重新告知或重新同意；需要时由服务端 capability／版本字段驱动 App，不能根据网页更新时间猜测。

## 4. 开发提醒门禁

Agent 或开发者开始以下模块前，必须主动提醒用户检查对应 H5、隐私清单和商店申报；提醒发生在编码前，不能等到发布时补文档：

| 开发触发项 | 必须提醒与同步的内容 |
|---|---|
| 登录、注册、找回账号、手机号换绑、一键登录 | 用户协议、隐私政策、运营商协议、手机号处理目的、协议确认时点 |
| 新增相机、相册、麦克风、位置、联系人、日历、通知、健康等权限 | 隐私政策、个人信息收集清单、权限前置说明、iOS Privacy Details、Google Data safety |
| 新增或更换短信、OSS、AI、OCR、地图、统计、崩溃分析、推送等第三方 SDK／Provider | 第三方信息共享清单、数据流、处理地区、保留／删除能力和商店申报 |
| Capture 媒体、Assistant、Memory、搜索答案等把用户内容发给第三方的能力 | 单独告知／同意、Provider 数据策略、撤回与删除路径，不能只依赖总隐私政策 |
| 账号删除、单项删除、自动清理、数据导出、撤回同意 | `/legal/account-deletion`、隐私政策的保留／删除说明、Web 请求链路和处理 SLA |
| 订阅、付费、自动续费、优惠活动 | 用户协议、付费／续费规则、退款说明；活动规则优先评估 H5 |
| 公开分享、帮助中心、FAQ、版本说明、运营活动、公开内容详情 | 先按本文件矩阵评估是否采用 H5，并确认分享 URL、SEO、过期策略和回到 App 的路径 |
| 新增功能、模块改版，或提出“无需发版即可上线” | 编码前记录 H5／React Native／原生版本载体决策；逐项检查权限、离线、核心状态、敏感写入、分享收益和失败降级 |
| 接入 `expo-updates` 或其他 OTA／动态更新机制 | 先做 ADR，明确签名、运行时版本、发布通道、灰度、回滚、监控、商店审核边界和旧二进制兼容；不能直接把生产包指向开发更新通道 |
| 上架 App Store／Google Play 或新增发行地区 | 检查正式 URL 可公开访问、无占位、关闭 JavaScript 仍可读、联系信息有效，并复核当地法律要求 |

如果触发项对应的运营主体、法务文本、Provider 或数据保留策略尚未确定，Agent 必须明确报告阻塞，只能完成结构、数据流和技术方案，不得发布占位政策或替用户作法律确认。

## 5. 分阶段实施

### 阶段 A：发布前必需

1. 产品负责人提供运营主体、联系方式、发行地区和经确认的协议／隐私文本。
2. 实现 `/legal`、`/legal/privacy`、`/legal/terms`、两张信息清单和 `/support`，并验证无登录、无 JavaScript、窄屏和动态字号。
3. 登录页接入协议确认与真实链接，“我的”接入法律与支持入口。
4. 在 App Store Connect 和 Google Play Console 填写正式 URL，并核对隐私申报。

### 阶段 B：账号与数据治理

1. 按现有删除状态机完成 App 内账号删除。
2. 新增中立 OpenAPI、验证码／reauth、幂等、限流和审计，实现 `/legal/account-deletion` Web 请求流程。
3. 补齐个人数据导出、撤回同意和第三方删除状态说明。

### 阶段 C：内容型 H5

在帮助、公开内容、运营活动、模板／案例、食谱／攻略和用户主动分享的只读内容出现真实需求后扩展。每个模块按第 1.4 节单独判断，不能因为已经有 H5 基础设施就默认迁移；核心任务管理与 AI 确认路径不迁移到 H5。

### 阶段 D：远程更新能力

已完成 `expo-updates` 客户端、`ADR-028`、test／production 频道、签名发布工作流和 OTA 安全变更检查。正式启用仍需创建 Expo Project，配置 GitHub Secrets，确认 EAS 端到端代码签名套餐，发布包含验签证书的新原生包，并依次完成测试频道、生产小比例灰度和回滚演练。完成前不把 OTA 作为用户可用能力。原生依赖、权限、SDK 和运行时不兼容变化始终重新构建并走应用商店发布。

## 6. 依据

- [Apple App Review Guidelines 5.1.1](https://developer.apple.com/app-store/review/guidelines/)：隐私政策必须同时出现在 App Store Connect 和 App 内，并说明收集、使用、第三方、保留、撤回与删除。
- [Apple App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/)：隐私政策 URL 必须公开可访问，并与商店数据申报一致。
- [Google Play User Data Policy](https://support.google.com/googleplay/android-developer/answer/10144311)：隐私政策需要有效、公开、非地区限制的非 PDF URL，并与 App 内数据处理一致。
- [Google Play 账号删除要求](https://support.google.com/googleplay/android-developer/answer/13327111)：允许创建账号的 App 同时需要 App 内删除路径和 Web 删除请求资源。
- [Expo Router 静态渲染](https://docs.expo.dev/router/web/static-rendering/)：静态输出会为路由生成 HTML，并复制 `public` 静态文件。
- [Expo EAS Update](https://docs.expo.dev/eas-update/introduction/)：OTA 适用于不改变原生运行时的 JavaScript、样式和资源；原生代码与依赖变化需要新构建，并且仍须遵守应用商店规则。
- [Expo Update 运行机制](https://docs.expo.dev/eas-update/how-it-works/)：更新只能加载到兼容的原生 runtime，项目必须显式管理 runtime version 与回滚。
- [Apple App Review Guidelines 4.7](https://developer.apple.com/app-store/review/guidelines/)：HTML5／JavaScript 功能仍由 App 开发者承担审核、隐私和数据责任，不得未经许可扩展原生能力或共享权限。
- [Expo Privacy Explained](https://expo.dev/privacy-explained)：EAS Update 请求包含操作系统、Expo Project ID 和用于更新分发的随机安装 Token；接入前必须把 Expo 纳入实际第三方处理者与隐私申报核对范围。
- [中华人民共和国个人信息保护法](https://www.npc.gov.cn/WZWSREL25wYy9jMi9jMzA4MzQvMjAyMTA4L3QyMDIxMDgyMF8zMTMwODguaHRtbD9yZWY9aW1i)：处理个人信息前应以显著、清晰方式告知处理者、目的、方式、种类、保存期限和权利行使路径。
