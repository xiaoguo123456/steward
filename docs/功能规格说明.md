# 1. 功能范围

## 1.1 MVP 核心闭环

MVP 以一次性交付完整核心体验为目标：用户可以通过文字、语音、图片或组合输入提交任何事务，AI 将多模态内容统一理解为可确认的候选结果；只有用户确认后的内容才进入计划、笔记或数据，未确认内容始终停留在 Capture 临时处理域。

```text
登录 / 初始化
    ↓
文字 / 语音 / 图片 / 组合 Capture
    ↓
AI 解析、必要追问与用户确认
    ↓
清单（Task / Event / Project）/ 笔记（Note）/ 数据（Tracker / Record）
    ↓
Today / Lists / Notes / Data / Search
    ↓
完成、修改、延期、安排、提醒、总结、撤销
```

MVP 包含：

- 账户登录与基础初始化
- 文字、语音、图片 Capture
- 图片＋文字、图片＋语音组合 Capture
- AI 解析
- Capture 对话内确认
- Task、Event、Project、Note、Record Object，以及独立的 TaskList 和 Tracker Schema
- Object 关联与重复检测
- Today
- 清单、笔记和数据三个正式内容模块
- 基础搜索与自然语言搜索
- AI Scheduler
- Daily Brief、Weekly Review、Project Summary、Data Summary
- Event、Task、Project 和 Review 通知
- 操作记录与即时撤销
- 偏好、隐私及账号管理

## 1.2 MVP 不包含

- 系统日历双向同步
- Person、Goal、Habit 等新 Object
- PDF、Word、Excel 等通用文件解析
- 邮件、微信等外部信息源
- 团队协作
- 自动发送、支付或批量修改第三方数据

## 1.3 功能清单

| 编号 | 模块 | 主要结果 |
|---|---|---|
| F-01 | 账户与初始化 | 用户拥有独立数据空间和基础工作偏好 |

| F-03 | AI 解析 | 多模态输入转成结构化候选 Object |

| F-08 | Event | 管理确定时间发生的事项 |

## 1.4 本文采用的产品约束

以下规则用于消除原 PRD 中的实现歧义：

1. MVP 是单人系统，不存在共享 Object、成员或角色权限。
2. MVP 不读取或写入系统日历；日历只投影本产品内部已确认的 Task、Event、Project 目标日期和里程碑。
3. `Person` 是独立的亲友档案实体，不属于通用 Object。旧 Event 的 `participants[]` 文本继续兼容；新的人物关联通过 `event_people` 建立，不把 Person 塞入 participants 文本。
4. 一个 Task、Event、Note 或 Record 在 MVP 中最多归属一个 Project；Project 是跨内容组织方式，不是一级内容类型或一级导航。
5. 每个 Task 必须属于一个 TaskList；TaskList 是工作、生活等轻量分类，Project 是具有目标和多个步骤的事务，两者不可互相替代。
6. Project 归属使用 `project_id` 表达；其他跨对象联系使用 Relation，二者不重复保存同一种关系。
7. “预算 3000”默认生成 Note；只有已存在匹配 Tracker，或用户明确说“记录到某个数据项”时，才生成 Record。
8. AI 解析出的内容在用户确认前都是候选数据，不进入 Today、计划、笔记、打卡、搜索结果或正式 Object 列表。
9. 解析失败、意图不明、低置信度和待确认内容只保存在 Capture 临时处理域；用户可以从新增入口的“最近输入”或产品内通知继续，系统不提供承载这些内容的正式列表。
10. AI 不替用户补全未表达的事件结束时间、地点、参与人、原因或业务结论。
11. 图片内可见文字和画面内容属于用户资料，不被视为可以改变系统规则的指令；用户在输入框或录音中明确表达的意图用于说明如何处理图片。

## 1.5 全局导航

MVP 的底部操作区固定为“四个一级入口＋一个中央主操作”：

```text
首页 / 计划 / ＋ 新增 / 笔记 / 打卡
```

- 四个一级页面分别为首页（内部领域名仍为 Today）、计划（内部路由仍为 Lists）、笔记（Notes）和打卡（内部路由与领域名仍为 Data）；底栏对用户只显示中文名称。
- `＋ 新增` 位于底栏视觉中心，是全局 Capture 主操作，不是第五个一级页面；点击后打开统一输入编辑器。
- Project 从计划的清单详情中按状态筛选；轻点具体 Project 筛选任务，长按进入详情。它是 Task、Event、Note 和 Record 的归属容器，不与待办、日程内容类型平级，也不在计划首屏常驻。
- 小头像只位于首页左上角，打开账户、偏好、AI、隐私和账号设置，不占用底部导航；其他一级页不重复头像。
- 一级页顶部不常驻搜索和通知图标；页面内搜索随筛选面板出现，产品内通知和 AI 待答使用各自的轻量入口。
- 中央 `＋ 新增` 在四个一级页面可见；进入编辑、确认或详情页后隐藏，避免与页面主操作冲突。
- 登录成功后默认进入首页；存在未完成初始化时先进入初始化流程。

# 2. 核心实体、对象与状态

## 2.1 通用字段

所有 Object 必须具有：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `id` | 是 | Object 唯一标识 |
| `type` | 是 | `task`、`event`、`project`、`note`、`record` |
| `title` | 是 | 用户可见标题 |
| `created_by` | 是 | `user`、`ai` 或 `system` |
| `provenance_refs[]` | 否 | 生成或更新本实体所依据的 Capture、Object 或 AI Action 引用 |
| `created_at` | 是 | 创建时间 |
| `updated_at` | 是 | 最后修改时间 |
| `deleted_at` | 否 | 软删除时间；非空时不出现在正常列表 |

`provenance_refs[]` 的每一项包含：

```text
source_type   capture / object / ai_action
source_id     来源实体 ID
source_revision 可选；Capture 来源的 revision
part_refs[]   可选；Capture 中的文字片段、音频时间段或图片区域
action        created_from / derived_from / updated_from
```

来源规则：

- 从 Capture 对话内确认创建的实体必须包含对应 Capture、revision 和 `part_refs[]`。
- 用户在表单中手工创建实体时，`created_by=user`，允许 `provenance_refs[]` 为空。
- AI 拆分 Task 时，新 Task 来源指向原 Task 和本次 AI Action；不要求虚构一个 Capture。
- 后续 Capture 更新已有实体时，保留原 `created_from`，追加本次 `updated_from`，不得覆盖首次来源。
- 来源已删除时保留来源类型、时间和“来源已删除”状态，不保留已删除的原始内容。

## 2.2 Task

Task 表示需要完成的行动。

| 字段 | 必填 | 规则 |
|---|---:|---|
| `title` | 是 | 不允许只包含空白字符 |
| `description` | 否 | 补充上下文 |
| `status` | 是 | 默认 `todo` |
| `priority` | 是 | `low`、`normal`、`high`，默认 `normal` |
| `due_date` | 否 | 只有日期、没有具体时刻的截止日 |
| `due_at` | 否 | 有明确日期和时刻的截止时间 |
| `due_timezone` | 否 | 设置 `due_date` 或 `due_at` 时必填，保存截止语义所属时区 |
| `scheduled_start_at` | 否 | 用户计划开始时间 |
| `scheduled_end_at` | 否 | 与开始时间成对出现，必须晚于开始时间 |
| `scheduled_timezone` | 否 | 设置计划时间时必填，保存计划所属时区 |
| `estimated_minutes` | 否 | 正整数 |
| `focus_date` | 否 | 用户明确指定在哪一天关注该任务 |
| `list_id` | 是 | 所属 TaskList；未指定时使用用户的默认清单 |
| `project_id` | 否 | 所属 Project |
| `reminders[]` | 否 | 基于 `due_date` 或 `due_at` 的一个或多个提醒；没有任何截止信息时不可设置 |
| `completed_at` | 否 | 状态变为 `done` 时写入 |

状态定义：

```text
todo       待办
doing      用户正在处理
done       已完成
cancelled  已取消
```

状态转换规则：

- `due_date` 与 `due_at` 互斥；用户补充具体时刻时，用 `due_at` 替换原 `due_date`，反之亦然。
- `todo` 可以变为 `doing`、`done` 或 `cancelled`。
- `doing` 可以变为 `todo`、`done` 或 `cancelled`。
- `done` 或 `cancelled` 重新打开后统一变为 `todo`。
- 截止时间、计划时间和 `focus_date` 只描述任务何时被关注，不参与状态推导；增加或清除这些字段不会自动改变 `status`。
- “随时可做”是 `todo` 且没有 `due_date`、`due_at`、计划时间和 `focus_date` 的查询筛选（API 参数仍为 `unscheduled`），不是 Task 状态。
- 删除不属于状态转换，删除后 Object 进入软删除状态。

截止语义：

- “明天交”“周五前完成”只生成 `due_date`，不得擅自补成当天 23:59。
- “明天下午 3 点前完成”生成 `due_at`。
- `due_date` 在 `due_timezone` 的该日期结束后才算逾期；界面始终显示“某日截止”，不显示虚构时刻。
- Today 收录先比较日期语义：若当前时刻换算到 `due_timezone` 后的当地日期不早于 `due_date`，该任务进入 Today；若已经越过该时区的日期结束边界，则进入“已逾期”。因此用户旅行换时区不会改变原截止日的事实语义。
- `due_date` 的通知必须由用户选择明确的当地触发时间；未设置时不自动假设提醒时刻。

## 2.2.1 TaskList

TaskList 是 Task 的轻量分类，用于表达“工作”“生活”“个人”等稳定分组，不承担 Project 的目标、进度和风险能力。

| 字段 | 必填 | 规则 |
|---|---:|---|
| `name` | 是 | 用户可见名称，同一用户下不可与未归档清单重名 |
| `color` | 否 | 只能从产品 Token 色板选择 |
| `icon` | 否 | 只能使用产品语义图标集合 |
| `position` | 是 | 用户自定义排序 |
| `is_default` | 是 | 每个用户恰好一个默认清单 |
| `archived_at` | 否 | 归档后不接收新 Task |

- 初始化时创建“默认清单”；用户可以重命名，但不能在没有替代默认清单时删除。
- 移动 Task 到另一 TaskList 不改变 Task 状态、时间或 Project 归属。
- 删除非空 TaskList 前必须选择将 Task 移到其他清单；归档只隐藏清单，不删除 Task。

## 2.3 Event

Event 表示在确定日期或时间发生的事项。

| 字段 | 必填 | 规则 |
|---|---:|---|
| `title` | 是 | 不允许为空 |
| `event_kind` | 是 | `schedule` 或 `important_date`；默认 `schedule` |
| `all_day` | 是 | 默认 `false` |
| `start_at` | 条件必填 | 定时 Event 的开始时刻；`all_day=false` 时必填 |
| `end_at` | 否 | 定时 Event 的结束时刻；未表达时保持为空 |
| `start_date` | 条件必填 | 全天 Event 的当地开始日期；`all_day=true` 时必填 |
| `end_date` | 否 | 全天 Event 的当地结束日期，包含该日；单日事件可为空 |
| `timezone` | 是 | 采用创建时用户时区 |
| `location` | 否 | 不根据历史记录自动填入 |
| `participants[]` | 否 | MVP 中仅保存文本名称 |
| `project_id` | 否 | 所属 Project |
| `note` | 否 | 事件说明 |
| `reminders[]` | 否 | 定时 Event 使用相对开始时间的提醒；全天 Event 使用明确的当地触发时间 |
| `recurrence` | 是 | `none` 或 `yearly`；只有 `important_date` 可以使用 `yearly` |

规则：

- 无法确定具体日期的“周末约一下王总”不能直接保存为 Event；用户确认行动意图后创建没有日期的 Task，并归入“随时可做”筛选。
- 日期明确、时间不明确的事项可以保存为全天 Event，但必须在对话内确认区明确展示“全天”。
- `all_day=false` 时只使用 `start_at/end_at`；`all_day=true` 时只使用 `start_date/end_date`，两组字段互斥。
- 全天 Event 的 `end_date` 早于 `start_date` 时禁止保存；定时 Event 的 `end_at` 不晚于 `start_at` 时禁止保存。
- 全天 Event 的提醒必须包含明确的当地触发时间，例如“当天 09:00”，不能只保存含义不清的“开始前 30 分钟”。
- `end_at` 为空时，时间线只显示开始时间，不在数据层假设默认时长。
- 修改 Event 时间后，相对提醒跟随新的开始时间重新计算。
- 生日、纪念日等稀疏但重要的日期保存为 `event_kind=important_date` 的全天 Event，在列表和日历中使用“重要日期”语义，不另建一级模块。
- `important_date` 可以按月日每年重复；2 月 29 日在非闰年显示于 2 月 28 日，并在详情中保留原始月日说明。普通日程和 Task 在 MVP 中仍不支持重复规则。

## 2.3.1 Person 与关联 Event／Task

`Person` 是用户主动建立的私人亲友档案，不属于通用 Object，也不从系统通讯录、聊天、通话或邮件中自动生成。

Person 保存姓名、`relationship_group`、可选关系称呼和备注；修改使用 `If-Match` 乐观锁。创建 Person 和人物 Event 均使用幂等键，并在当前用户的 RLS 事务中执行。

- 首版只支持手动添加亲友，不申请整本通讯录权限；以后若接入系统联系人，优先使用按人选择并同步更新个人信息清单、权限用途和应用商店申报。
- 点击人物进入独立全屏详情页，提供“添加任务”和“添加事件”。未来安排、生日和纪念日创建正式 Event 并通过 `event_people` 关联人物；“为某人做一件事”创建正式 Task 并通过 `task_people` 关联人物。详情按“待办、近期安排、重要日”分区展示，不提供“记互动”或历史互动列表。
- Task 与 Person 的关联不改变 TaskList 归属、状态机、Today 收录、提醒和完成语义。同一 Task 可以继续从原清单、Today、搜索和人物详情进入；人物详情默认只显示 `todo/doing`，完成后从待办区消失。
- 人物详情的待办圆圈直接复用 Task 完成 Command，并携带当前 `version`；标题区域继续打开任务详情。完成成功后刷新 Task／Today 查询，版本冲突或网络失败时不得本地伪装完成。
- 删除 Person 时同步删除其 `event_people` 和 `task_people` 关联，但不删除已经存在的 Event 或 Task。早期 `PersonInteraction` 数据和接口只为已发布旧版 App 保留兼容，不再由新客户端读取或写入，兼容窗口结束后再执行删除迁移。
- AI 本期不读取或向 Provider 发送 Person 内容，也不生成带人物关联的 Task Proposal。以后启用前必须增加亲友资料的明确开关、最小字段发送、同名消歧、可追溯来源和 Proposal 确认，并更新个人信息／第三方清单；手动路径不依赖 AI。

## 2.4 Project

Project 表示需要多个步骤才能完成的事务集合。

| 字段 | 必填 | 规则 |
|---|---:|---|
| `title` | 是 | 项目名称；界面字段标签显示“项目名称” |
| `description` | 否 | 项目范围或结果说明 |
| `status` | 是 | 默认 `active` |
| `start_date` | 否 | 开始日期 |
| `target_date` | 否 | 目标完成日期 |
| `progress` | 是 | 系统计算，只读 |

稳定状态：`active`、`paused`、`archived`。契约继续接受 `completed` 作为“标记完成”命令和历史兼容值，但完成后立即归档，不长期保存或展示独立的已完成分组。

状态转换规则：

- 新建 Project 默认为 `active`。
- `active` 可以变为 `paused` 或 `archived`；请求标记完成时，在确认后直接写为 `archived`。
- `paused` 可以恢复为 `active` 或变为 `archived`；请求标记完成时同样直接写为 `archived`。
- 历史 `completed` 数据升级时并入 `archived`，恢复表示重新打开为 `active`。
- `archived` 可以恢复为归档前状态；系统必须记录 `status_before_archived`。
- Project 从完成归档恢复时，不改变关联 Task 的状态。
- 删除不属于状态转换，删除后进入软删除状态；恢复删除时回到删除前状态。

进度规则：

```text
progress = 已完成 Task 数 ÷（全部 Task 数 - 已取消 Task 数）
```

- Project 没有关联 Task，或全部 Task 均已取消时，显示“暂无有效任务”，不显示 `0%` 造成误导。
- Project 标记完成时，不自动完成其未完成 Task；系统必须先提示仍有多少未完成事项，用户确认后自动归档 Project。
- Project 归档后默认不出现在“全部项目”结果，但可以通过“已归档”状态筛选找到。

## 2.5 Note

Note 表示值得保存、但当前不需要行动的信息。

| 字段 | 必填 | 规则 |
|---|---:|---|
| `title` | 是 | AI 可以从内容生成，用户可修改 |
| `content` | 是 | `NoteContent` 判别联合；每篇只使用 `plain_text` 或版本化块文档中的一个权威分支，普通 Note 当前创建纯文本，心情日记使用 `blocks_v1` |
| `attachments[]` | 否 | 图片或受支持的附件引用；MVP 不解析通用文件正文 |
| `tags[]` | 否 | 用户自定义标签，同一 Note 内去重 |
| `pinned_at` | 否 | 置顶时间；为空表示未置顶 |
| `project_id` | 否 | 所属 Project |

Note 没有完成状态。用户可以编辑、置顶、添加标签、移动到 Project、转换为 Task 或删除。正文和附件属于信息保存，不会因为缺少日期或行动字段进入待处理队列。

## 2.6 Tracker 与 Record

Tracker 是一组可复用的数据字段；Record 是某次实际记录。

Tracker 是独立的 Schema 实体，不属于 Object，也不作为 Relation 的端点；Record 属于 Object。AI 创建 Tracker 时返回 Tracker Candidate，用户确认后先创建 Tracker，再写入后续 Record。

Tracker 字段：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `id` | 是 | Tracker 唯一标识 |
| `user_id` | 是 | 所属用户 |
| `name` | 是 | 例如“体重”“直播数据” |
| `schema` | 是 | 一个或多个字段定义 |
| `status` | 是 | `active` 或 `archived` |
| `archived_at` | 否 | 进入归档的时间；恢复使用时清空 |
| `created_by` | 是 | `user`、`ai` 或 `system` |
| `provenance_refs[]` | 否 | 生成或更新该 Tracker 所依据的来源引用 |
| `created_at` | 是 | 创建时间 |
| `updated_at` | 是 | 最后修改时间 |
| `deleted_at` | 否 | 软删除时间 |

MVP 字段类型：

- `number`
- `currency`
- `percentage`
- `duration`
- `text`

每个 schema 字段必须包含：字段名、字段类型、是否必填、可选单位。

自定义 Tracker 的管理界面只提供保存与归档，不提供直接删除。归档后保留 30 天并允许恢复；满 30 天仍未恢复时，系统自动软删除 Tracker 及其 Record。恢复后再次归档必须重新开始 30 天计时，旧清理任务不得误删新一轮归档数据。内置 Tracker 不进入这条自动删除规则。

Record 字段：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `title` | 是 | 系统根据日期和主要字段生成，例如“2026-08-12 · 体重 72.3 kg” |
| `tracker_id` | 是 | 所属 Tracker |
| `timestamp` | 是 | 该数据实际发生时间 |
| `values` | 是 | 必须满足 Tracker Schema |
| `note` | 否 | 本次记录说明 |
| `project_id` | 否 | 可选所属 Project |

## 2.7 Relation

MVP 支持以下非归属关系：

| 关系 | 示例 |
|---|---|
| `requires` | Event“项目会”需要 Task“准备报价” |
| `related_to` | Note“预算约 30 万”与 Event“项目会”有关 |

规则：

- Project 归属只使用对象自身的 `project_id`，不再同时创建 `contains` Relation。
- Relation 必须记录 `created_by`：`ai`、`user` 或 `system`。
- Relation 必须记录与实体相同结构的 `provenance_refs[]`。
- Capture 解析创建的 Relation 必须在 Capture 对话内确认区中与 Object 一起展示；其他 AI 功能创建 Relation 时，必须在对应功能的确认界面展示。
- 删除某个 Object 时，其 Relation 一并失效，不删除另一端 Object。

# 4. F-02 全局 Capture

**载体决策**：Capture 输入、AI 管家对话、处理中状态、澄清、候选确认／编辑、保存与撤销均保持 React Native 原生核心流程。本次不新增 H5，不涉及个人信息／第三方清单、单独同意或应用商店申报变化。

## 4.1 入口

所有一级页面必须提供统一的 `＋ Capture` 入口。

点击后在当前页面上方弹出底部 Capture 输入面板，不跳转全屏页面，也不要求用户先选择内容类型。全局 `＋ Capture` 默认进入语音优先的未录音状态，但打开面板不会自动申请权限或开始录音；行程票据等明确的媒体入口可以按上下文突出图片入口。面板采用渐进展开：

- 未录音时只突出一个“点击说话”麦克风主操作，图片与键盘作为次要入口。
- 点击麦克风后才申请权限并开始录音，不使用“按住说话／松开发送”。
- 录音中显示波形、时长、暂停、完成与取消；暂停后可以继续或完成。
- 录音结束后显示可试听的语音草稿，并提供重录、删除和“发送并整理”。
- 文字模式显示多行输入框，图片与麦克风作为次要入口。
- 已添加的图片、录音和错误状态只在实际存在时展示。
- 通用空白面板的底部输入工具栏在“图片”“键盘”旁提供同规格“新建任务”，进入字段全部可见的确定性 Task 表单；不得使用脱离工具栏的单独文字链接。已有任一输入内容或处于行程等专用 Capture 上下文时隐藏。中央 `＋` 不展开 Task、Event、Note 等类型选择菜单。

用户点击输入面板外的遮罩、关闭按钮或系统返回时关闭面板，不改变当前一级页面。文字、语音和图片入口不得在首层同时展开成多块说明卡片；“最近输入”只有取得真实未完成数量时才显示，不得使用固定占位数量。

MVP 支持五种输入组合：

| 输入模式 | 输入组成 | 典型用途 |
|---|---|---|
| 文字 | 一段文字 | 直接描述任务、日程、项目或记录 |
| 语音 | 一段录音 | 口述杂乱事项，由系统转写和整理 |
| 图片 | 一张或多张图片 | 解析截图、照片、海报、手写内容或表格 |
| 图片＋文字 | 图片加一段文字说明 | 用文字告诉 AI 如何处理图片或补充图片外信息 |
| 图片＋语音 | 图片加一段录音说明 | 用口述告诉 AI 如何处理图片或补充上下文 |

同一次 Capture 至少包含一种输入。MVP 不把 PDF、Word、Excel、视频或其他文件作为图片处理。

## 4.2 Capture 内容结构

一个 Capture 由有序的 `input_parts` 组成：

```text
Capture
├── text（0 或 1 项）
├── audio（0 或 1 项）
└── image（0～9 项）
```

系统根据最终输入组成写入唯一 `input_mode`：

```text
text         仅文字
audio        仅语音
image        仅图片
image_text   图片＋文字
image_audio  图片＋语音
```

Capture 还必须记录递增的 `revision`。第一次提交锁定 revision 1；提交后修改文字、修订转写、替换／删除／增加图片或调整图片顺序时，在同一个 Capture ID 下创建新的 revision，并使旧 revision 的候选结果失效。单纯重试同一个失败输入项不增加 revision。

每个输入项至少记录：

| 字段 | 说明 |
|---|---|
| `part_id` | 输入项唯一标识 |
| `type` | `text`、`audio` 或 `image` |
| `sequence` | 在本次 Capture 中的顺序 |
| `raw_asset_ref` | 音频或图片的受控存储引用；文字为空 |
| `normalized_text` | 原始文字、语音转写或图片 OCR 结果 |
| `analysis_metadata` | 音频时间段、OCR 区域、图片画面事实和质量信息；文字可为空 |
| `processing_status` | 当前处理状态 |
| `error` | 当前输入项的失败原因 |

规则：

- 图片顺序必须保留，用户可拖动调整顺序。
- 用户主动输入的文字与原始录音互斥，因此只形成本文定义的五种输入模式；用户修订语音转写不视为额外的文字输入。
- 已有文字时点击录音，或已有录音时开始输入文字，必须提示用户选择“替换原输入”或“取消切换”，不得静默清空。
- 用户说“第一张”“最后一张”“上图”等表达时，按提交时图片顺序解析。
- 所有候选字段必须能追溯到一个或多个 `part_id`，必要时定位到图片区域或文字片段。
- 语音转写和图片 OCR 是派生内容，不覆盖原始音频或图片。

## 4.3 统一编辑器行为

| 编号 | 功能要求 |
|---|---|
| CAP-001 | 所有输入项为空时，提交按钮不可用。 |
| CAP-002 | 文字最多 10,000 个字符；超出时阻止提交并显示剩余需删减字数。 |
| CAP-003 | 一次最多添加 9 张图片，用户可以预览、排序、替换和删除。 |
| CAP-004 | 支持 JPEG、PNG、HEIC 和 WebP；单张原图不得超过 20 MB。 |
| CAP-005 | 支持普通照片、长截图和包含文字的图片；动图只读取第一帧并向用户说明。 |
| CAP-006 | 同一次 Capture 最多保留一段录音；重新录制前必须让用户确认替换。 |
| CAP-007 | 用户退出未提交的编辑器时，询问保存草稿或放弃；草稿只保存在当前账号。 |
| CAP-008 | 在线且用户确认上传后创建 Capture 记录并锁定本次 revision；离线时只进入设备队列。稳定幂等键避免重复点击、崩溃恢复或后台重试造成重复数据。 |
| CAP-009 | 上传或解析期间允许关闭 AI 管家浮层，处理继续进行；当前 App 会话可从常驻 AI 管家入口回到同一对话上下文，进程重启后可从“我的 → 最近输入”恢复。确认保存前不出现在任一正式内容列表。 |
| CAP-010 | 同一 Capture 重试必须复用同一个 Capture ID，不得重复创建正式 Object。 |

图片上传前可以在设备端压缩，但必须满足：

- 不改变方向和图片顺序。
- 不裁掉画面内容。
- 不得因压缩导致文字、数字、二维码周边说明或图表标签不可辨认。
- 默认移除 GPS、设备型号等与内容理解无关的 EXIF 信息。

## 4.4 文字输入

- 文字可以是待处理内容，也可以是对图片的操作说明。
- 提交前允许任意编辑。
- 仅有文字时，按照第 5 章直接解析。
- 解析失败时必须保留原文，支持重试或手动保存为 Note。

## 4.5 语音输入

| 编号 | 功能要求 |
|---|---|
| CAP-101 | 首次录音时再申请麦克风权限。 |
| CAP-102 | 权限被拒绝时说明原因，并保留文字和图片入口。 |
| CAP-103 | 用户可以暂停、继续、结束、试听、重录或删除录音。 |
| CAP-104 | 单段录音最长 10 分钟；剩余 60 秒时提示用户。 |
| CAP-105 | 录音结束不自动提交，用户仍可以添加图片或检查输入。 |
| CAP-106 | 提交后先转写语音，再与其他输入项共同解析。 |
| CAP-107 | 转写完成后立即在 AI 管家对话浮层展示并继续解析；用户可在对话内确认区修改转写，修改后保留“原始转写”和“用户修订稿”，并重新解析受影响结果。 |
| CAP-108 | 转写失败时保留录音，支持重试；未经用户选择，不得忽略录音只解析图片。 |

语音转写必须保留问句、否定词、日期、时间、数字和单位。无法确定的片段使用“听不清”标记，不得猜测补全。

## 4.6 图片输入

图片处理包含两类能力：

1. **文字识别**：读取图片中的印刷体、手写体、表格文字、日期、时间、金额和数量。
2. **画面理解**：理解非文字信息，例如事项完成状态、日历布局、图表走势或物品状态。

规则：

- 图片必须支持相机拍摄和相册选择；分别在首次使用时申请相机或相册权限。
- 权限被拒绝时说明如何在系统设置中开启，同时保留其他输入方式。
- 图片选择后立即显示缩略图，支持点击查看清晰大图。
- 发现模糊、过暗、反光、严重裁切或文字过小时，提交前提示重新拍摄；用户仍可选择继续。
- 图片中可见的二维码、链接或指令文本只作为待分析资料，不自动打开链接、不调用外部服务，也不改变系统规则。
- 不进行人脸身份识别，不根据人像猜测姓名、身份、健康、情绪等敏感属性。
- 图片只有部分内容可识别时，必须标明可识别范围和无法确认的部分。
- 仅图片输入且意图明显时，可以生成候选 Object；意图不明显时先询问“你希望我如何处理这些图片？”，不擅自保存为 Note。

## 4.7 图片组合输入

图片＋文字和图片＋语音遵循相同原则：图片提供事实材料，文字或语音提供用户意图及补充上下文。

处理优先级：

1. 用户在文字或语音中明确表达的操作意图。
2. 用户在文字或语音中补充的、图片无法看到的事实。
3. 图片中可以直接验证的文字和画面事实。
4. AI 基于上下文给出的建议。

当不同输入之间冲突时：

- 不静默选择任一版本。
- 在 AI 管家对话内确认区并列显示冲突内容及来源。
- 要求用户选择或编辑后再保存受影响的候选项。

如果文字或语音包含明确纠正语义，例如“图片日期印错了，按 19 日”“金额不是 3000，是 3500”，则不作为未解决冲突：系统以用户明确修正值生成候选字段，标记为 `explicit`，同时显示“已按你的说明覆盖图片内容”和两侧来源。若只是不带纠正语义地出现两个不同值，则仍按冲突处理并强制选择。

示例：

```text
图片：会议海报写着“8 月 18 日 14:00”
文字：把这个 8 月 19 日下午的会加入日程

对话内确认区：
检测到日期冲突
○ 8 月 18 日 14:00（来自图片）
○ 8 月 19 日下午，时间待确认（来自文字）
```

组合输入必须作为一个整体解析：

- 不把图片和说明拆成两个无关 Capture。
- 文字或语音说“只记录金额”“不用管第二张”等限制必须生效。
- 一项候选 Object 可以同时引用图片和文字／语音作为来源。
- 同处于一个 Capture 只代表输入被一起提交，不代表其中所有事实必然相关；除非用户表达或内容证据能够支持，否则不得仅因共同提交而创建 Relation。
- 文字或语音与图片明显描述两件独立事情时，可以分别生成候选 Object，并在对话内确认区分组展示。
- 删除某个输入项后，必须重新解析所有依赖该输入项的候选结果。

## 4.8 提交与处理流程

```text
编辑输入
  ↓
上传图片 / 音频
  ↓
语音转写 + 图片文字识别与画面理解
  ↓
多模态内容合并
  ↓
Object 与 Relation 解析
  ↓
AI 管家对话内确认
```

语音转写与多张图片处理可以并行，但进入 Object 解析前必须确保用户选择保留的输入项均已成功处理。

AI 管家对话浮层必须逐项展示处理状态，例如：

```text
✓ 文字已读取
✓ 语音已转写
✓ 图片 1 已识别
… 图片 2 正在识别
! 图片 3 过于模糊
```

同一 Capture 的原始文字和历次补充回答在处理中合并显示为一条“文字与补充说明已读取”，
不得随 revision 数量重复堆叠；图片仍按编号逐项展示，以便精确重试或替换。用户回答追问后，
服务端必须把“问题—回答”成对并按时间正序交给解析器，不能把回答扁平化为无角色的独立素材。
已经明确回答的信息不得因上下文乱序而再次追问；不设置追问次数硬上限，是否继续追问只由仍未解决的真实信息缺口决定。

部分失败时：

- 明确指出失败的是哪段录音或哪张图片。
- 允许重试、替换、删除失败项。
- 用户可以明确选择“忽略失败项并继续”，系统必须在对话内确认区持续显示“结果未包含某项输入”的警告。
- 未经用户选择，不得在缺少输入项的情况下静默继续解析。

## 4.9 Capture 状态

Capture 主状态：

```text
draft               编辑中
submitting          正在提交和上传
preprocessing       正在转写语音或识别图片
parsing             正在合并理解并生成候选结果
awaiting_instruction 存在阻塞解析的问题，等待用户补充说明
needs_confirmation  等待用户确认
confirmed           用户已确认且保存事务成功
partially_failed    部分输入项失败，等待用户处理
failed              整体处理失败，可重试
discarded           用户放弃
expired             长期未处理，原始输入已按保留规则清理
```

每个图片和音频输入项还必须单独记录 `pending`、`processing`、`succeeded`、`failed` 或 `ignored`，以支持单项重试并区分“系统失败”和“用户明确忽略”。

主状态转换规则：

| 当前状态 | 用户或系统动作 | 下一状态 |
|---|---|---|
| `draft` | 提交 | `submitting` |
| `submitting` | 上传全部成功 | `preprocessing`；只有文字时直接进入 `parsing` |
| `submitting` | 上传整体失败 | `failed` |
| `preprocessing` | 所有保留输入项成功 | `parsing` |
| `preprocessing` | 部分输入项失败 | `partially_failed` |
| `preprocessing` | 所有媒体输入项失败且没有可用文字 | `failed` |
| `partially_failed` | 重试或替换失败项 | `preprocessing` |
| `partially_failed` | 明确忽略失败项 | 将其标为 `ignored` 后进入 `parsing` |
| `parsing` | 生成候选结果 | `needs_confirmation` |
| `parsing` | 生成阻塞型 `unresolved_questions`，包括仅图片意图不明 | `awaiting_instruction` |
| `parsing` | 整体解析失败 | `failed` |
| `awaiting_instruction` | 用户通过全局待答入口或 Capture 补充文字说明 | 新 revision 进入 `parsing` |
| `awaiting_instruction` | 用户补充语音或图片说明 | 新 revision 进入 `preprocessing` |
| `needs_confirmation` | 修改任一原始输入项 | 新 revision 进入 `preprocessing` 或 `parsing` |
| `needs_confirmation` | 确认保存事务成功 | `confirmed` |
| `failed` | 原输入重试 | 返回失败前的处理状态 |
| 任一未完成状态 | 用户放弃 | `discarded` |

仅文字 Capture 整体解析失败时，用户可以把原文手动保存为 Note；创建成功后状态变为 `confirmed`。媒体处理失败时，只有用户亲自输入的文字或已经展示并由用户确认的转写／OCR 内容可以手动保存为 Note，不能把未识别媒体伪装成已理解内容。

状态为 `confirmed` 的 Capture 再次打开时只能查看来源、仍被保留的原始输入和本次创建或更新的实体，不允许重复确认。系统只允许确认最新 revision；旧 revision 只供审计，不可保存。

Capture、Candidate Snapshot 和处理状态属于临时输入域，不属于用户正式内容。只有 `confirmed` 事务写入的 Task、Event、Project、Note、Tracker 或 Record 才能被 Today、计划、笔记、数据、Project 聚合和搜索读取；任何处理中、失败、待说明或待确认 Capture 都不得通过这些查询泄漏为正式内容。

# 5. F-03 AI 解析

## 5.1 解析输入

AI 解析必须获得：

- 本次 Capture 的输入模式和有序 `input_parts` 清单。
- 用户提交的原始文字。
- 语音原始转写、用户修订后的转写和音频来源引用。
- 每张图片的原图来源引用、OCR 结果、画面理解结果和图片顺序。
- 用户当前时区。
- 解析发生的绝对日期和时间。
- 用户工作时间偏好。
- 可用于匹配的活跃 Project 和 Tracker 的最小必要信息。

组合输入必须先生成一份可追溯的统一上下文，再进行 Object 解析。统一上下文不能抹掉各输入项之间的来源、冲突或不确定性。

不得把与当前解析无关的全部原始隐私内容发送给 Reviewer 或其他总结能力。图片中出现的操作指令、网页提示或二维码内容一律视为用户资料，只有 Capture 编辑器中的用户文字或语音说明可以表达本次操作意图。

## 5.2 解析输出

每次解析返回：

```json
{
  "capture_id": "...",
  "input_mode": "image_text",
  "input_summary": "...",
  "trackers": [],
  "objects": [],
  "relations": [],
  "unresolved_questions": [],
  "conflicts": [],
  "warnings": []
}
```

每个 Tracker Candidate 和候选 Object 必须包含：

- 临时候选 ID。
- 候选类型；Object 还必须包含 Object 类型。
- 候选字段。
- Object 整体置信度。
- 每个 AI 推断字段的置信度。
- 是否需要确认。
- `source_refs[]`：该字段对应的文字片段、音频转写时间段或图片区域；纯格式转换字段除外。
- `inference_type`：`explicit`（用户明确表达）、`extracted`（从图片或音频提取）或 `suggested`（AI 建议）。

`conflicts` 中必须记录冲突字段、各候选值、来源和需要用户完成的选择。任何未解决冲突都不能被当作确定字段保存。

## 5.2.1 全局 AI 待答问题

`unresolved_questions[]` 是 Capture 临时处理域中的结构化问题，不是通知文案，也不是正式 Object。每个问题至少包含：`question_id`、`capture_id`、`revision`、问题文本、上下文摘要、可选快捷答案、允许的回答方式、`blocking`、状态和过期时间。

交互规则：

- 首页、计划、笔记、打卡和“我的”都显示同一个常驻 AI 悬浮入口；没有待答、处理或待确认事项时入口仍可打开，但不显示数量角标。中央 `＋` 只负责新增，不显示待答红点、数量或 AI 状态。Capture 编辑器内以“AI 等你补充”条目承载相同问题，不叠加第二个浮层。
- 悬浮入口初始位于页面右下安全区；用户拖动超过 8dp 后进入移动状态，移动范围限制在当前页面安全区内，松手后在 200ms 内吸附到最近的左侧或右侧。拖动不能同时触发打开对话，同一 App 会话内按“停靠侧 + 相对高度”保留位置，跨页面和页面尺寸变化时仍可恢复到可见区域。
- 入口一次只展开一个当前问题，优先级依次为阻塞当前解析、即将过期、更新时间较早；其余问题只显示数量，不连续弹窗打断用户。
- 点击入口进入统一对话流：先显示最小来源上下文和 AI 的具体问题，再提供快捷答案、文字、图片或语音回答；关闭面板等同于稍后回复。Capture 提交后的上传、处理中状态、失败恢复、澄清、候选确认与编辑、保存结果都在同一浮层中追加，不跳转独立处理页或确认页。图片选择和预览留在对话输入区，提交后立即复用原 Capture 的上传、处理与确认链路，不在 Assistant Turn 内复制媒体协议。
- `blocking=true` 的问题使 Capture 停留在 `awaiting_instruction`；非阻塞问题可以与 `needs_confirmation` 并存，用户选择“暂不确定”后按显式空值继续，不得由 AI 猜测。
- 回答必须绑定 `question_id + capture_id + revision`。服务端接受回答后在同一个 Capture 下创建新 revision，并让旧问题变为 `answered`；旧 revision、已回答、已跳过或已过期问题不得再次回答。
- 回答会作为用户消息追加在原对话中；处理时显示可读的回复中状态，整理完成后直接追加可编辑候选与确认操作，不再要求点击“查看并确认”跳页。最终确认事务成功后清除该事项的角标与待处理状态，但 AI 管家入口继续常驻。
- 待答入口只能显示最小上下文摘要，不得把完整原文、图片、转写或候选字段投影到正式模块；关闭入口不会放弃 Capture。
- 系统通知只是用户离开 App 后的可选补充；产品内待答入口始终可用，不能依赖用户授予推送权限。
- 提醒的主路径是**站内浮出**：到点的提醒出现在首页顶部，点击进入对应事项，「知道了」之后这一次发生不再出现。系统推送尚未接入，接入后复用同一份到期判定。
- 提醒是否过期按**事件本身**算，不按提醒触发时刻算：一条「提前 7 天」的提醒响过 5 天时，事件可能还有两天才到，那正是最该看到它的时候。事件本身过去 3 天后不再打扰。

## 5.2.2 通用 Assistant 对话连续性

- 通用 Assistant 默认按用户资料中的 IANA 时区维护“今天的对话”。打开对话面板时，服务端查找当地自然日内最近一次发生用户消息的 active Thread；存在时立即恢复消息，不先闪现空状态。
- 当天没有可恢复 Thread 时展示空状态，但仅打开或关闭面板不得创建 Thread。用户真正发送第一条消息时才创建当天 Thread。
- 当天再次从默认入口发送消息时复用当天最近使用的 Thread，不使用滚动分钟数判断；跨过当地自然日后默认新建另一天的对话。
- AI 回复即使在午夜后完成，也不能单独把昨天的 Thread 变成今天的默认对话；自然日归属以用户消息时间为准。
- 用户可以显式开始新对话，也可以从历史列表继续旧 Thread。显式新对话发送首条消息，或旧 Thread 在当天收到新的用户消息后，它成为当天后续默认恢复的最近对话。
- 对话输入支持最多 9 张图片，可从相册选择或拍照并在发送前删除。纯文字继续创建 Assistant Turn；只要包含图片，就复用统一媒体上传和 `origin=assistant` 的 Capture 链路，文字作为第一 Part、图片按预览顺序追加，处理完成后仍须在当前对话内确认。
- 日期边界和默认 Thread 选择只由 Go 服务端确定，移动端不得按设备时间自行推断；待确认 Action Proposal 仍按独立状态读取，不因切换 Thread 自动执行或丢失。

## 5.3 置信度规则

| 置信度 | 对话内确认行为 |
|---:|---|
| `>= 0.85` | 默认填入并选中，用户仍需最终保存 |
| `0.60～0.84` | 填入但高亮提示用户检查 |
| `< 0.60` | 不作为确定值保存，显示为空或待选择，并提出问题 |

整体置信度不能替代字段置信度。例如 Event 类型判断很确定，但时间不确定时，时间字段仍必须单独提示。

图片和语音还必须遵循：

- OCR 或转写对数字、日期、时间、单位的置信度低于 `0.85` 时必须高亮。
- 图片被遮挡、裁切或存在多个相似数值时，即使模型整体判断较高，也必须降低对应字段置信度。
- 同一事实同时来自多个一致的输入项时可以提高置信度，但必须保留全部来源。
- 用户修订后的语音转写按用户明确输入处理；原始转写仍保留用于追溯。

## 5.4 时间理解规则

| 用户表达 | 处理规则 |
|---|---|
| “明天下午 3 点” | 按用户时区解析为次日 15:00，并在对话内确认区显示完整日期 |
| “周五下午” | 日期可解析，时间不够明确；要求用户选择时间 |
| “周末约王总” | 创建没有日期的 Task 候选，不创建确定 Event；确认后归入“随时可做”筛选 |
| “下个月提醒我续费” | 创建 Task 并要求确认具体日期；MVP 不创建独立 Reminder Object |
| “明天交报价” | 创建 Task，写入明天的 `due_date`，不补具体时刻 |
| “明天下午 3 点前交报价” | 创建 Task，写入用户时区下的 `due_at` |
| “开会一小时” | 可以根据明确时长生成 `end_at` |
| 只说“下午 3 点开会” | 若日期无法从当前上下文确定，则询问日期 |
| 解析出的时间已过去 | 显示警告，要求用户修改或仍然保存 |

补充规则：

- 一周按周一至周日计算。
- Event 未提及结束时间时，`end_at` 必须为空。
- Task 的“提前准备”时间属于 AI 建议，不能伪装成用户明确表达的截止时间。
- 所有相对时间在对话内确认区中必须转换为可读的绝对日期和时间。

## 5.5 类型判断规则

- 用户明确指定“任务、日程、笔记、记录到某个 Tracker”时，显式意图优先。
- 有明确行动动词且需要完成：Task；没有日期也可以是有效 Task，确认后进入计划的“随时可做”筛选。
- 有明确发生日期或时间、且语义是届时发生的事项：Event。
- 需要多个步骤推进的目标或行程：Project；Project 作为清单中的组织对象，同时可以关联 Note 和 Record。
- 当前不要求行动、无需按固定字段重复统计的事实、资料和上下文：Note。
- 明确写入已有 Tracker，或明确要求创建结构化模板和记录：Record／Tracker Candidate。
- 数字、日期或金额本身不足以把内容判断为 Record；不存在唯一匹配 Tracker 时必须要求用户选择或按 Note 保存。
- 类型无法可靠确定时在 Capture 对话中追问，不能先创建正式内容再让用户清理。
- 一段输入可以生成多个 Object，并建立 Relation。
- 一组图片可以共同生成一个 Object，也可以分别生成多个 Object；必须依据内容语义而不是图片数量决定。
- 图片中的清单项在用户要求“变成待办”时生成 Task；没有该意图时不自动把所有文字行转成 Task。
- 类型存在歧义时，对话内确认区必须允许用户切换类型。

## 5.6 不允许的推断

AI 不得：

- 自动生成用户没有表达的会议结束时间。
- 因为历史上在某地点见过某人，就自动补充本次地点。
- 把“可能”“大概”改写成确定事实。
- 在没有 Tracker 的情况下把孤立金额默认当作财务 Record。
- 根据数据变化编造变化原因。
- 因同名人物或 Project 自动选择唯一关联目标。
- 把图片里的示例文案、广告文案或界面按钮默认当成用户任务。
- 根据图片中的人脸、衣着或环境猜测个人身份或敏感属性。
- 在图片或语音部分处理失败时，假装已经完整理解全部输入。

# 6. F-04 Capture 对话内确认

## 6.1 对话内确认内容

AI 管家对话浮层按输入语义分组展示：

- Tracker Candidate 卡片。
- 候选 Object 卡片。
- Object 之间的关系。
- 不确定字段和警告。
- 原始输入区：文字、可播放音频、语音转写和按顺序排列的图片。
- 输入冲突区。
- 本次将保存的项目数量。

每张卡片必须支持：

- 选中或取消选中。
- 修改类型。
- 修改字段。
- 删除当前候选项。
- 查看字段来源；文字定位到片段，语音定位到对应时间段，图片定位到对应图片和区域。

组合输入的对话内确认区必须做到：

- 用户不离开当前对话浮层即可在候选卡片和来源图片／转写之间切换。
- 图片缩略图保持提交顺序，并标注“图片 1、图片 2”等编号。
- 文字或语音说明中的限制条件以醒目方式显示，例如“只处理第一张”。
- 存在日期、金额、名称等跨输入冲突时，先显示冲突选择，再允许保存受影响候选项。
- 用户修改原始文字、转写或替换图片时，提示将重新解析；确认后废弃旧候选并生成新候选。

## 6.2 保存规则

| 编号 | 功能要求 |
|---|---|
| CFM-001 | 存在未解决的必填字段时，不允许保存对应候选项。 |
| CFM-002 | 用户可以只保存本次解析中的部分候选项。 |
| CFM-003 | 保存按钮显示实际保存的 Tracker 与 Object 数量，例如“保存 4 项”；Relation 不单独计数。 |
| CFM-004 | 一次确认中的 Tracker 与 Object 创建、已有实体更新及 Relation 变更必须以事务方式保存；任一操作失败时整体回滚。 |
| CFM-005 | 重复点击保存不得创建重复 Object。 |
| CFM-006 | 保存成功后展示创建结果和即时撤销入口。 |
| CFM-007 | 未选中的候选项视为用户放弃，不进入任何正式内容列表；原始 Capture 仍可追溯。 |
| CFM-008 | 没有选择任何新建或更新项时，保存按钮不可用；用户可返回修改输入或放弃本次 Capture。 |

部分保存必须满足依赖闭包：

- Task Candidate 未明确指定 `list_id` 时，对话内确认区显示并预选用户默认 TaskList；默认清单不可用时阻止保存并要求选择其他清单。
- 选择一个引用“本次新建 Tracker”的 Record 时，自动联动选择该 Tracker；用户若取消 Tracker，必须同时取消 Record，或把 Record 改绑到已有 Tracker。
- Relation 不作为独立勾选项。只有两端实体都将存在时才保存：一端候选被取消时，该 Relation 自动取消；另一端是已有实体时不受影响。
- Object 的 `project_id` 指向本次候选 Project 时，选择 Object 会联动选择 Project。用户取消 Project 时，必须选择“同时取消这些 Object”或“保留 Object 但清空 `project_id`”。
- 更新已有实体的候选项可以单独选择；依赖该更新后字段的其他候选项被保留时，系统必须提示依赖关系并阻止产生无效引用。
- 对话内确认区必须在用户操作时即时显示联动影响，不能等到保存失败后再提示。

## 6.3 同名与重复处理

当存在多个可关联的同名 Project 时：

```text
你指的是：
○ 新官网项目
○ 品牌官网改版
○ 不关联项目
```

内容重复检测在当前用户的未删除实体中执行，归档和已完成实体也参与。MVP 使用以下确定性候选规则：

| 类型 | 重复候选条件 |
|---|---|
| Event | 归一化标题完全相同，且定时 Event 开始时间相差不超过 15 分钟；全天 Event 的 `start_date` 与规范化后的 `end_date` 均相同（空 `end_date` 按 `start_date` 处理） |
| Task | 归一化标题完全相同、所属 Project 相同，且二者均未完成或取消 |
| Project | 归一化名称完全相同，且已有 Project 不是 `archived` |
| Note | 归一化标题和正文摘要完全相同 |
| Record | `tracker_id`、`timestamp` 和规范化后的 `values` 全部相同 |

标题／名称归一化只执行：去除首尾空白、连续空白合并、英文转小写、统一全角半角标点。不得使用不可复现的语义相似度直接拦截保存。

满足上述条件时只标记“可能重复”，不自动合并或覆盖。以 Event 为例：

```text
这个日程可能已经存在：
[更新原日程] [仍然创建] [取消本项]
```

MVP 必须同时保证确认接口幂等和基于内容的重复检测。

- “更新原内容”会把当前 Capture 作为 `updated_from` 追加到已有实体的 `provenance_refs[]`，原创建来源保留。
- Task、Project、Note 和 Record 使用同样的“更新原内容／仍然创建／取消本项”选择，其中字段不兼容时先进入编辑比较页。
- Relation 候选若 source、target 和 relation type 完全相同，则直接复用已有 Relation 并追加来源，不创建第二条。

# 7. F-05 计划

## 7.1 页面组成

计划只展示已经确认保存的日期与行动事实，并读取 TaskList、Project 作为归属与筛选信息，不展示 Capture、候选结果、解析失败或待说明内容。计划首屏是任务与时间入口，不直接铺开完整任务流：

| 入口 | 主要内容 | 展示规则 |
|---|---|---|
| 今天／明天／已完成 | 对应时间范围或完成状态的完整 Task 列表 | 在同一条紧凑入口栏显示名称和数量 |
| 随时可做 | 已确认但没有截止、计划或关注日期的 `todo` Task | 独立显示数量；进入后可以直接完成、加入今天、设置日期或打开详情 |
| 清单 | 用户的 TaskList | 统一成组列表，不区分 AI／用户创建来源 |
| 日历 | Task、Event、重要日期和 Project 目标日期的日期投影 | 从右上角进入独立二级页面，默认完整月视图，可切换按周选择日期的周历视图 |

“今天、明天、已完成”只是稳定时间入口，不使用“智能清单”分组标题，也不与普通 TaskList 形成来源层级。计划首屏不显示标签区、Project 快捷栏、筛选面板或列表／日历切换；标签、Project、状态和关键词筛选在进入具体清单或时间列表后渐进提供。“随时可做”按 2.2 的字段条件计算，不是新的实体或状态；没有日期的明确 Task 仍保留在原 TaskList，同时聚合到“随时可做”，不强行进入日历。“加入今天”只写入当天 `focus_date`；“设置日期”写入 `due_date` 和用户时区。“随时可做”详情不重复展示用途说明；空列表只显示“暂无内容”，不追加同义副文案。

日历是计划的独立二级页面，不占底部一级导航，也不以一次性弹窗出现。它必须按选中日期统一返回以下正式事实：Task 的排期／截止日期、普通 Event、`important_date` Event 和 Project `target_date`，并满足：

- 默认展示包含用户当地今天的完整 6 周月格；左上角返回，右上角始终显示完整年月，点击后打开按年份选择 12 个月的面板。页面提供“月历／周历”显示方式切换，切换时保留选中日期。月格顶部固定显示“周日”至“周六”。
- 每个日期格只展示排序后的第一条安排预览，标题固定取前 4 个 Unicode 字符并限制为一行，超过 4 个字的部分直接不渲染，不换行、不显示省略号，也不显示“另 N 项”等第二行数量提示。月格不得为容纳更多标题而缩小字号，也不得仅用类型圆点代替文字；完整标题和同日其他安排从当日安排或周历到达。
- 月格下方不常驻重复的“今日安排”。点击任意日期后，从底部打开该日安排面板，展示当天全部标题、时间和类型；空日期只提示“这一天还没有安排”。
- 周历使用周日至周六的 7 天横向日期条，显示当前周日期范围和每天事项数量；点击日期后只在下方展示该日全部安排，不连续铺开整周。用户可以通过左右按钮或在日期条上横向滑动切换前后周，切周时保留同一星期位置。手机竖屏不渲染 7 列时间网格。
- 当前 Project 范围继续生效；切换 Project 后月格预览、数量、周历和当日安排同步刷新。
- 月格预览使用不同但克制的语义底色；当日安排和周历同时使用图标、类型文字与标题区分普通日程、待办、重要日期和里程碑，颜色不是唯一的类型识别方式。
- 只展示已确认且未删除的内部事实，不读取或写入系统日历，也不把 Record 时间、更新时间或系统通知时间混入日历。
- 全天 Event 按 `start_date/end_date` 收录；定时 Event 按用户时区映射日期；Task 按 `scheduled_date`、`due_date` 或定时计划日期进入对应日，不把无日期 Task 强行放进日历。
- `important_date` 按其当地月日投影年度发生日期；Project `target_date` 只作为只读“项目目标”投影，打开后进入 Project 详情，不复制创建 Event。

## 7.2 TaskList 管理

- 页面按用户自定义顺序展示 TaskList，并提供新建、编辑、排序、归档和恢复入口；编辑可以修改名称、语义图标和 Token 颜色。
- 计划首屏不使用含义宽泛的“管理”文字入口；活动清单末尾固定显示“新建清单”。存在两个及以上活动清单或已有归档清单时，标题右侧显示标准更多图标，点击后直接进入独立“编辑清单”页面，不再弹出中间菜单；排序和已归档清单统一在该页面处理。
- 排序与归档清单进入独立“编辑清单”页面；活动清单整行可上下拖动，不额外显示重复的拖动图标。点击活动清单右侧更多图标直接打开编辑面板，名称、颜色和图标选择默认全部展开，不再要求点击图标二次展开。
- 所有活动清单使用同一套外观与操作，不展示“默认”标签，也不固定某个图标。清单从产品预置语义图标和六种 Token 颜色中选择，不接收任意图片或 Emoji；创建时按名称推荐图标并优先分配未使用颜色，用户手动选择后不再被名称覆盖。
- 编辑面板的保存按钮下方直接提供等宽“归档”按钮，按钮本身不附加保留期说明；归档成功后使用 Toast 提示实际自动删除时长。至少保留一个活动清单；归档当前内部默认清单时，服务端自动把默认任务落点转移到另一个活动清单，不让用户处理这项内部规则。
- 已归档清单的更多面板不再展示编辑字段，只提供“恢复清单”和红色“删除清单”；删除前必须确认，确认后服务端把其中 Task 迁入当前默认清单并立即软删除原清单。未主动删除时，归档清单在服务端配置的可恢复期内可以恢复；到期后执行同样的迁移与软删除。保留期由 `STEWARD_TASK_LIST_ARCHIVE_RETENTION` 集中配置，默认 `72h`，客户端根据接口返回值生成 Toast 文案。
- 新建 Task 默认进入用户默认清单；创建或确认时可以改选清单。
- 具体 TaskList 和“随时可做”详情在列表末尾提供“添加任务”，空状态沿用同一操作。具体 TaskList 预选当前 `list_id`；“随时可做”预选默认 TaskList 且不预设 `due_date`、`due_at`、排期或 `focus_date`。Project 筛选生效时不显示不含 Project 字段的快捷入口。
- TaskList 条目显示未完成 Task 数，不展示 Capture 待确认数。
- 打开某个 TaskList 后只展示该清单中的 Task；Project 作为可选二级筛选，不替代 TaskList。
- 清单详情直接展示“全部项目、进行中、已暂停、已归档”Project 状态胶囊，窄屏自然换行且不隐藏。选择某个状态后在下一行直接显示该状态下的具体 Project；轻点 Project 胶囊筛选任务，长按进入该 Project 详情，不再显示笼统的“管理”入口。辅助功能同时提供可发现的“打开项目”操作，不把长按作为无障碍用户的唯一入口。
- 空清单显示“这里还没有任务”，提供“添加任务”，不提供“清理未确认内容”。新建 TaskList 只从计划首屏“清单”末尾的“新建清单”进入。

## 7.3 Project 入口与跨内容关系

- Project 从计划的具体清单或时间列表进入项目筛选器；它不占用一级导航，也不与待办、日程平级。
- 项目选择器必须支持全部项目、无项目、最近使用和名称搜索；选择后立即更新待办或日程结果，并把本次项目提升为最近使用。
- 单个 Project 的打开与状态操作从具体 Project 胶囊进入，不设置独立管理入口；新目标仍从统一 Capture 描述，由 AI 生成候选并经用户确认。
- Project 可以聚合 Task、Event、Note 和 Record；这些内容仍分别出现在计划、笔记或数据模块。
- 用户在 Project 内通过带当前 Project 上下文的 Capture 新增内容；确认后写入最终 `project_id`，同时遵守该内容自身的必填字段，Task 仍必须写入一个 TaskList。
- Capture 未能确定 Project 归属时必须在确认流程中让用户选择“某个 Project”或“不关联”，不得先保存再进入待关联队列。

# 8. F-06 首页（Today 聚合）

## 8.1 页面组成

用户可见一级页面名称固定为“首页”，Today 保留为内部领域名、聚合接口与路由名。“今天”用于日期范围、清单筛选和首页内部分区标签，不作为一级页面名称。

首页按以下顺序展示：

1. 小头像、页面标题和日期。
2. “今天／时光／心情／亲友”顶部标签导航。
3. “今天”分区内的 4×2 生活场景快捷入口。
4. Today Tasks。
5. 仅在存在有效内容时展示 AI Daily Brief，界面名称为“今日提醒”。

首页不单独展示 Event、Today Records 或最近更新；Event 从计划的日历视图查看，Record 从打卡模块查看。不得用 `Today.events` 的数量或标题拼装“今日安排”等第二个今日摘要，也不得把逾期 Task 混入指向日历的卡片。

### 8.1.1 首页顶部标签导航

- 标签固定按“今天、时光、心情、亲友”排序；“首页”仍是底部一级导航名称，四个标签只切换首页内部内容，不增加底部 Tab 或新的一级路由。
- 标签栏支持点击和自身横向滚动，当前项同时使用高对比文字和短下划线表达；每项触控高度不小于 44dp，并提供 `tab` 语义与选中状态。不得只依赖颜色表达选中。
- 标签栏随首页纵向滚动吸顶。内容区域不使用整页左右滑动切换：照片浏览和亲友关系筛选都可能使用横向或连续手势，不能与页级 Pager 竞争。
- App 冷启动首次进入首页时默认选中“今天”，并继续使用正式 Today Query、下拉刷新和既有查询结果；用户从时光、心情或亲友的二级／更深页面原路返回时，必须保留离开前的首页分区，不得跳回“今天”。需要跨栈回到某个分区时，可以通过一次性路由参数指定，首页消费后立即清理该参数。切换其他标签只改变客户端页内视图，不修改 Today 收录、排序、查询缓存或领域状态。
- 当前迭代交付“时光”“心情”“亲友”正式能力。亲友通过正式 OpenAPI、生成 Client、Go Domain 和用户隔离查询保存用户主动录入的人物，以及人物与 Event／Task 的关联；Task 继续归属原 TaskList，不装载本地演示内容，也不请求联系人权限。时光通过正式 OpenAPI、媒体直传、Go Domain 和用户隔离查询保存私人照片记录，不再装载本地演示内容。音乐不进入当前首页信息架构。
- 首页不再提供独立“灵感”分区，也不提供灵感专属全屏 Assistant 模式。主动提问、自由思考和内容整理统一由全局 AI 管家入口承载，避免形成并行入口与重复人格；既有 Note、Note 标签、通用 Assistant、Capture 和 Proposal 数据与能力不受影响。

### 8.1.2 其他后续分区载体与 AI 边界

- 三个非 Today 分区默认使用 React Native 原生页面：时光依赖媒体选择和本地生命周期，亲友涉及私密人物资料与关系筛选，心情属于高频私密输入；公开只读分享以后可以单独评估 H5，但编辑、权限和确认保持原生。
- 时光未来的 AI 核心能力是根据用户主动选择的媒体及已有 Object／Event 来源生成关联候选和描述文案；候选经用户确认后再发布，且必须保留纯手工选择媒体和填写描述的路径。当前 V1 在第三方图片处理者、单独同意、`memory_moment_writing_candidate` Schema、审计和 Eval 完成前不启用 AI，也不得用本地模板伪装模型结果。
- 亲友人物关系能力保持原生分区。当前 AI 不读取或发送人物资料，也不生成带人物关联的 Task Proposal；若以后开放，其核心能力只能从用户主动选择的内容生成 Person／Relation／Reminder／Task Candidate，或基于用户明确授权的已确认事实生成可追溯简报。同名人物、身份和敏感事实不确定时必须由用户选择。AI 不读取聊天、通话或整本通讯录，不进行关系评分，不直接创建人物、关联或提醒；手动添加、手动关联和手动提醒始终可用。
- 心情的 AI 核心能力是对用户主动保存的心情记录生成可追溯的阶段摘要与温和建议；不得诊断心理疾病、推断未填写的敏感事实或把模型结论当成确定事实，手工记录路径不依赖 AI。
- 任一分区开始正式写入前，必须先完成 OpenAPI、生成 Client、服务端用户隔离、幂等、来源、删除与保留策略；AI 只能生成 Candidate／Proposal，不能直接写数据库。

### 8.1.3 时光分区 V1

#### 定位与内容规则

- 时光是“把用户主动留下的照片整理成可长期回看的个人生活时间线”，不是系统相册镜像、纯文字日记或家庭社交空间。
- 每条时光必须包含 1～9 张图片；不支持纯文字创建。描述为可选补充，没有文字时仍可仅凭照片发布。
- 同一天可以存在多条时光。V1 不读取 EXIF，也不提供补记日期或手工改日期；服务端以接收发布请求的时刻按账号时区生成发布日期，客户端不得自行推断或提交该日期。
- 发布是不可逆的内容边界：照片顺序和描述只允许在发布前整理。发布成功后服务端不提供更新接口，用户只能查看或删除整段时光；V1 不支持编辑描述、替换照片、删除单张照片或重新排序。
- 第一版不提供家庭邀请、点赞评论、访客记录、人脸库、公开分享、打印、付费扩容、后台整库扫描或根据 EXIF 位置自动创建足迹。

#### 浏览与查找

- 首页采用照片主导的纵向时间线，按年份和月份分组；日期数字作为视觉锚点，不使用装饰性时间轴竖线或嵌套卡片。
- 1 张图片使用横向主图；2 张使用等高双图；3 张使用一张主图加两张小图；4～9 张在首页只展示前三张并在末张显示剩余数量，详情页展示全部。
- 首页年份右侧使用带文字的“按日期”和“选照片”上下文动作，不使用与底栏中央全局 Capture 重复的圆形加号。“按日期”进入独立查找页；有内容的日期显示品牌色标记，点击日期后展示当天时光，日历不长期占用首页首屏。
- 顶部标签不启用整页左右滑动；详情内同一条时光的图片可以左右浏览，两者不得产生手势竞争。

#### 新建、发布与 AI 边界

- 用户点击首页或月历中的“选照片”时，直接打开系统照片选择器并主动选择 1～9 张图片，再在发布页通过三列九宫格预览、移除或继续添加照片，并可填写描述。照片按系统选择与后续追加顺序发布，页面不显示序号或排序控件。用户取消系统选择器后保留空发布页和再次选图入口，未选择图片时不能发布。
- 相册选择优先使用系统 Photo Picker 或等价的选择性授权能力，不为浏览少量指定图片申请整库读取；拍照只在用户主动选择“拍照”时申请相机权限。
- 发布时先通过正式媒体上传授权把用户主动选择的图片写入私有对象存储，再调用 `POST /v1/memory-moments` 原子保存顺序和描述；服务端在同一创建命令中生成发布日期。请求必须带稳定幂等键；上传或发布失败时保留当前页面内仍可用的选择和文字并允许重试，不能把失败显示为已发布。
- 当前 V1 只提供确定性的手工路径，不显示“帮我整理”或本地 AI Candidate，也不把图片或正文发送给 Provider。以后启用 AI 前必须完成单独同意、第三方清单、最小上下文、AI Schema／Eval 和可编辑 Candidate；AI 失败不能阻止手工发布。
- 时光是独立照片领域，不与 AI 长期记忆 `memory_items` 混用；服务端只接受已完成上传且属于当前用户的图片引用。

#### 详情与状态

- 详情页展示全部图片、发布日期和可选描述；顶部和底部均不提供编辑入口，唯一写操作是“删除这段时光”。删除确认必须明确整段内容和服务端媒体副本将进入删除流程，系统相册原文件不受影响，且当前不提供恢复。
- 列表、详情和删除必须按当前用户隔离；其他账号读取或删除同一 ID 时统一表现为资源不存在。删除成功后条目立即从列表、月历和详情不可见，直接删除仍被有效时光引用的媒体必须被拒绝。
- 必须覆盖首次空状态、正常、加载、媒体读取失败、上传失败、离线、日期无内容和删除失败。任何失败都保留页面内仍可用的图片和用户已填写文字；不得回退到 Fixture 或本地演示条目。
- 图片加载前保留稳定宽高比，首屏主图优先加载；列表滚动不得因图片解码频繁跳动。所有图标按钮触控范围不小于 48dp，并提供读屏名称。

### 8.1.4 心情日记正式范围

“心情”分区正式形态为私人心情日记，而不是独立的情绪打卡器、心理咨询入口或通用聊天页面。它围绕“写下此刻—按日期回看—形成阶段回望”组织体验，心情结构和花园反馈服务于日记正文，不取代正文。通用“笔记”继续承担资料、灵感和工作内容的整理；心情日记按日期与个人感受组织，并且不得默认混入笔记首页、Project 聚合或普通笔记标签流。

日记记录遵守以下规则：

- 同一天允许保存多篇独立日记；移动端新建时以用户实际保存日记的当前时刻填写 `occurred_at`，`created_at` 只用于审计。按用户时区和 `occurred_at` 分组，不能用服务器创建时间代替日记日期；新建入口不接受历史日期预选，也不提供补写能力。
- 每篇日记正文必填，标题可选。用户可以选择五级心情、低／中／高三级精力、最多三个感受词和少量场景词；除正文外均可跳过，不能把一次书写变成强制问卷。
- 写作入口支持快速记录和自由书写，两者最终保存同一种正式日记：快速记录突出“一句话＋心情”，自由书写直接进入空白正文。第一阶段编辑器不内置写作提示或引导问题，不让用户在开始书写前额外处理可跳过卡片。
- 编辑器不提供手动富文本工具栏，只保留用户主动触发的“AI 排版润色”。首次调用必须取得心情日记 AI 单独同意；请求只包含当前 `blocks_v1` 正文，不包含心情、精力、其他日记或长期偏好。模型返回结构化候选后由 Go 校验原块 ID 与顺序、数字、日期、链接和文档上限，结果只回填可撤销草稿；用户点击“完成”并回传 `ai_action_id` 后才保存并记录来源。
- 日记正文使用版本化块文档，第一版格式为 `blocks_v1`。支持普通段落、二／三级标题、无序列表、有序列表、引用和分隔线；文字片段支持加粗、斜体、删除线和 `http/https` 链接。不得保存任意 HTML、CSS、字体、字号、颜色、脚本、嵌套表格或客户端私有节点。
- 每篇 Note 只能有一个权威正文表示：现有普通笔记可以继续使用 `plain_text`，心情日记固定使用 `blocks_v1`。服务端从权威正文确定性派生只读 `plain_text` 投影，用于列表摘要、搜索、导出降级和经用户授权的 AI 输入；客户端不得提交或修改该投影，也不能让它与块文档分别演进。
- `blocks_v1` 中每个块具有稳定 ID，列表第一版不嵌套，标题只允许二／三级。正文总文字、块数量、链接协议和单块长度都由 Contracts 给出上限并由服务端重验；空格式、只有分隔线或只有空白文字不满足正文必填。
- 第一阶段不创建图片块、音频块或文件块。后续媒体正文使用新的文档 Schema 版本和私有 Asset ID，不在块 JSON 中保存 Base64、设备路径或长期签名 URL；旧客户端遇到不支持的文档版本只能用服务端纯文本投影只读，不能降级覆盖保存。
- 首页默认显示当天按时间倒序的日记时间线，不再在书写入口下方重复展示月份标题或最近七天日期条。页面顶部使用同一行的“搜索日记／按日期”紧凑按钮，搜索入口占据剩余宽度，“按日期”固定在右侧，两者高度、垂直中心和间距对齐且触控高度不小于 44dp。“按日期”进入独立心情日历页，交互与时光的日期查找保持一致：完整 6×7 月格、前后月切换、年份／月份选择和选中日全部日记；点击日记进入详情。日历页只用于按日期浏览，不提供“写日记”或“补写”入口；首页写作入口始终创建当前日记，日期按实际保存时刻计算，不能预选或修改为历史日期。搜索仍使用独立二级页面，并且只查当前用户的心情日记。
- 每篇日记可以单独设置“不参与 AI 回望”和“不出现在往日回忆”。关闭后立即从后续 AI 选材、阶段摘要或回忆投影中排除；已经生成但尚未确认保存的候选也必须失效。
- 删除日记后立即从时间线、日历、搜索、回望轨迹、AI 上下文和回忆投影中不可见，并按正式删除策略清理正文、派生摘要与索引。删除文案不得承诺尚未实现的备份物理清理时限。

周／月回望使用同一个原生页面，心情首页只保留“本月回望”入口。回望页把日记密度和时间分布的只读生成式轨迹、确定性统计、感受词和可选 AI 深度回望放在一条连续内容流中，不再提供独立“心情花园”入口。每篇已保存日记形成一个完整的几何花瓣、光点或轨迹节点，点击后回到对应日记。不同心情只影响有限的明度、密度与形态，不使用五套高饱和色；低落、疲惫或未选择心情的记录同样完整呈现，不得出现枯萎、死亡、连续打卡中断惩罚、排名或带羞辱感的评价。视觉轨迹不建立第二份业务事实，所有节点都从正式日记确定性投影。

AI 能力分为三个明确入口：

- 排版润色：用户在编辑器主动点击后，模型只处理当前草稿的文字和块结构，不分析其他日记，不直接保存；失败保留原文，成功后可继续编辑或撤销。
- 保存后追问：用户保存日记后可以主动选择“继续想一想”，模型只基于当前这篇正文生成一个温和、可跳过的追问；回复形成用户继续编辑或新增的草稿，未经保存不能改写原日记。
- 周／月回望：先展示由 Go 确定性计算的篇数、心情分布和常用感受词；用户再主动选择“生成 AI 回望”、时间范围和允许使用的日记。AI 输出只包含简短摘要、带来源日记 ID 的观察、反思问题和温和建议，不能输出诊断、确定性人格结论或医疗建议。

AI 默认关闭正文分析时，客户端只请求确定性统计，不向 Provider 发送日记正文。开启“深度回望”必须单独同意，并支持全局关闭和逐篇排除；Provider 请求只发送本次用户选中的最小正文与日期，不发送无关账户、Project、位置或媒体信息，不用于模型训练。AI 回望与原日记分开显示，逐条标注来源日期；保存回望属于显式确认动作，模型结果不得自动写入 Note、Memory 或其他 Domain。

第一阶段正式范围包含基础块文档日记、心情结构、独立日历浏览、日记内搜索、本地草稿与离线恢复、编辑删除、含心情轨迹的周／月回望、单独同意后的一键 AI 排版润色和可关闭的保存后追问。照片、语音、定位、健康数据、公开分享、多人日记、全量日记自由聊天、连续打卡奖励、应用锁和系统通知提醒不进入第一阶段；正式发布 AI 排版润色前必须确认实际 Provider、敏感数据等级、处理地区、训练退出、保留与删除能力，并同步隐私政策、个人信息清单、第三方清单和应用商店申报。

## 8.2 生活场景快捷入口

- 首页固定展示 8 个可点击入口，每行 4 个，默认顺序不得由 AI 静默改变：
  1. 第一行：运动、食谱、番茄钟、记账。
  2. 第二行：重要日、购物、复盘、更多。
- 运动、食谱、番茄钟和记账属于高频主动行为，位于首行；食谱与购物上下相邻，番茄钟与复盘上下相邻；“更多”固定在右下角，符合低频聚合入口的常见位置。
- 入口必须具备按钮语义、可读标签、按压反馈和不小于 44dp 的点击区域；点击后进入对应场景页，不展示无行为占位。
- 场景页只组合已有领域能力，不新增同义 Object：运动、番茄钟和打卡数据复用 Tracker / Record，购物复用 TaskList / Task，重要日复用 Event 或日期投影，复盘复用 Review，“更多”只负责二级导航。
- 食谱是唯一的例外，它有自己的资源：菜谱内容是平台共享的只读数据；本周菜单、饮食档案与收藏是用户数据。菜单要支持整周替换、按格调整和版本冲突判定（见 8.2.2），这些行为塞进一条 Note 表达不出来。购物清单仍然复用 TaskList / Task，不新增与之同义的食材待办类型。
- “更多”扩展功能中心只展示当前可到达且未在一级模块重复的功能，不放置无法点击的“开发中”占位，也不显示通用介绍卡或页尾说明。首版只保留“行程”；饮水、睡眠和阅读继续由 Tracker / Record 与“打卡”页承载，家庭事务继续由计划与清单承载。
- “行程”进入独立总览与详情路由，而不是计划日历。它以 Project 为组织对象，组合 Event、Task、Note、附件和 Relation 展示按天安排、预订资料与行前清单，不创建新的 Trip Object 或平行数据表。
- AI 可以根据上下文提供建议，但创建或更新正式数据仍必须经过用户确认，并遵守对应 Schema、状态机与来源记录规则。
- 后续可以提供用户手动排序；未实现手动排序前保持固定顺序，不根据点击频次或模型判断自动重排。

### 8.2.1 运动场景

- 运动入口进入独立二级流程，第一版支持户外跑步、健走、骑行和力量训练四种真实可选模式，不把未实现能力展示为占位按钮。
- 页面流程包含运动首页、运动准备、运动进行中、运动总结和历史记录。运动首页只负责提供四种运动的直接入口和最近两条记录，不显示默认选中态、目标、开始按钮或周频次；用户点击运动后进入准备页，再完成目标、播报与训练计划确认；总结页由用户主动确认是否保存。
- 户外运动准备页必须先选择目标类型再调整目标值：跑步、健走和骑行均支持自由、距离、时长；距离和时长提供步进、滑杆与常用快捷值。达到目标只触发提醒，不自动结束记录；切换目标类型时使用该类型的合理默认值。
- 户外跑步、健走和骑行使用地图主导的进行中页面。跑步和健走显示距离、时间与平均配速，骑行显示距离、时间与平均速度；力量训练使用动作、组数、次数与休息计时，不复用户外地图模板。
- 产品面向普通人培养运动习惯，目标与数据表达优先清晰、低压力和可持续，不使用竞技排名、专业训练负荷或黑色运动科技视觉作为默认体验。
- 运动模块不提供音乐播放。户外模式提供确定性的语音播报开关：GPS 就绪后倒数开始，暂停、继续、整公里、目标完成和结束时播报；跑步与健走的整公里播报包含本公里配速和总用时，骑行包含平均速度和总用时。运动过程中不得依赖在线模型临时生成播报，以免弱网导致提醒缺失；品牌音色可以由语音模型离线生成并缓存。
- 进入户外运动页后申请“使用 App 时”定位权限。首次获得精度不差于 30 米的有效 GPS 坐标后才倒数开始计时和路线记录，定位等待期间保持 `0.00` 和 `00:00`，也不累计漂移距离。开始后以前台 GPS 坐标绘制真实路线并计算距离、平均配速或平均速度；地图使用 MapLibre 加载 CDN 上的 PMTiles 资源。权限拒绝、定位服务关闭和地图加载失败必须给出明确状态与重试或设置入口。
- 暂停、打开结束确认或离开页面时停止采集；继续运动后开启新路线段，不把暂停期间的位移连成直线。当前不申请后台定位，不上传或持久化原始坐标。
- 总结页预填 GPS 距离并允许用户修正；用户确认后通过既有 Tracker / Record 写入时长和距离。健走不展示步数目标，不手动补填或保存步数。

### 8.2.2 食谱场景

- 食谱入口进入独立二级流程，内部只提供“本周”和“发现”两个同层级视图，不增加一级 Tab。“本周”默认选中今天，并允许通过七天日期栏浏览本周其他日期的早餐、午餐和晚餐。
- 本周菜单展示的能量与蛋白质是**这份方案本身的估算量**，即照这个菜单做出来有多少，不是用户的摄入。用户加不加餐、在外面吃了什么不在本功能追踪范围内，文案不得表述为“你的摄入”，也不得据此推断用户实际吃了多少。用户主动记录的实际摄入是 Record，两者不混在一起展示。当前来源未提供可靠膳食纤维数据，界面不展示该项，导入与菜单抽取不得推测、补零或作为筛选依据。用户可以替换单道菜、调整当天或重新生成整周菜单。整周生成与批量调整始终先作为预览，由本周首页日期栏下方、菜单内容之前的“确认食谱”统一保存；该入口必须在生成完成后的首屏可见，不得藏在长菜单页底。单道“换一道”先展示同餐次、同角色的候选确认弹窗，用户在弹窗确认后立即保存当前整周菜单，不得再要求滚动到页底二次确认。
- 首次使用可以完成四步饮食问卷，也可以跳过后直接浏览菜谱。未完成问卷时仍可浏览，但点击生成本周菜单须先进入饮食档案，不得用默认档案发起生成。问卷收集健康目标、年龄／性别／身高／体重／目标体重／活动水平、过敏与忌口，以及用餐人数、口味、预算、烹饪时间、厨具和常备食材。身体数据必须说明用途并允许后续修改；过敏原和明确禁忌属于确定性硬过滤条件，AI 排序不得覆盖。
- 健康目标第一版支持均衡饮食、减脂、增肌和一般健康控糖。一般健康控糖只用于推荐少添加糖、优先全谷物、增加膳食纤维和规律进餐的日常菜谱，不提供疾病诊断、治疗承诺或用药建议；用户声明已确诊糖尿病或正在用药时，不自动生成治疗型菜单，并提示结合医生或营养师建议。
- “发现”支持按菜名或食材搜索，并提供快手菜、时令、减脂、增肌、健康控糖等分类和图片内容流。分类与搜索须由服务端查询全库，不得只过滤客户端已加载的前 100 条。无搜索词时，每次重新进入发现页按本次浏览会话和分类稳定打乱展示顺序；进入详情再返回时保持原顺序，下拉刷新后换一批。搜索结果保留服务端相关性顺序，不参与随机展示。时令按中国自然上市旺季建立版本化食材四季库，只展示当前季节命中的菜；春季为 3—5 月、夏季为 6—8 月、秋季为 9—11 月、冬季为 12—2 月，按中国时区自动切换，不需要逐月维护。模型只离线补充食材知识，输出经 Schema 校验后由确定性导入规则使用，不直接写库。减脂沿用来源明确标签并校验能量，增肌按蛋白质含量与供能占比筛选，健康控糖按清淡、碳水与明确添加糖保守筛选且不用于疾病饮食建议。推荐项必须显示可解释原因，不使用没有明确计算依据的健康评分。
- 菜谱详情至少展示图片、份量、耗时、难度、营养估算、食材数量和步骤。步骤以左侧数字作为唯一序号，先显示做法文字，再显示对应图片，没有步骤图片时不占位。来源、授权与图片权利继续作为内容入库的内部合规字段，不在详情页单独展示“内容来源”区块。烹饪模式使用大字号分步操作，并支持上一步、下一步和步骤计时。加入某天某餐、收藏、标记做过或记录实际摄入均须由用户主动触发。
- 一餐是一组菜而不是一道：早餐为主食加蛋白，午餐与晚餐为主食、荤菜、素菜各一。挑中「单品成餐」（面、盖饭、蛋包饭一类本身已含主食与蛋白的菜）时，它顶替主食与荤菜两个位置，午晚只再配一道素菜。午餐与晚餐结构相同，份量差别由餐次热量占比（早 25%、午 40%、晚 35%）体现，不用道数区分。
- 每日热量目标由身高、体重、年龄、性别与活动量按 Mifflin-St Jeor 估算，再按目标调整（减脂 −20%、增肌 +10%）。热量有硬下限（女 1200、男 1500 千卡），低于下限时夹住并明确告知用户。身高、体重、年龄缺任何一项都不得估算，此时退回按营养排名选菜并提示补全，不得使用默认身体数据代入计算。性别未填时按男女公式中间值估算并说明精度。碳蛋脂按目标设定供能占比，蛋白质另有按体重的下限，两者取高。以上均为一般性能量估算，不构成诊断、治疗或用药建议。
- 整周菜单由服务端的确定性代码生成，不调用模型：过敏原与忌口是硬过滤，任何情况下都不放宽；填不满时留空并说明，不得为了排满而放宽过敏原。热量目标是候选筛选条件而非排序权重——只作为打分项时偏差会逐格累积。同一份饮食档案与同一个 seed 必然给出同一份菜单，「换一批」是递增 seed。生成结果只是预览，仍须用户点击「确认食谱」才写入。
- 平台菜谱内容需标注其在一餐中的角色（主食、单品成餐、荤菜、素菜）；甜品饮品、烹饪教程与营养估算明显不合理的条目标记为不参与菜单生成，但仍可浏览与搜索。未标注角色的菜谱不参与生成。
- 菜谱的早餐、午餐和晚餐适用范围由平台确定性规则维护，不能把内容来源的餐次标签原样当成推荐结论。咖喱、炒饭、焖饭和火锅等明显偏午晚餐的菜不进入早餐自动生成，但仍可在发现页浏览并由用户主动加入；来源标签继续保留用于审计。
- 生成时做的任何妥协（放宽了最长烹饪时间、候选不足导致重复、某一格无菜可排）必须随结果返回并展示给用户。默默给出一份筛剩下的菜单，用户无从判断是自己筛得太狠还是功能出错。
- 从已确认菜单生成购物清单时，先合并重复食材和份量，并默认勾选全部食材；用户可以取消不准备购买的项目。确认后把食材合并进用户唯一的活动购物 TaskList，同名未完成商品合并份量，不按周重复创建清单。购物 Task 不进入计划、Today、日历、搜索和复盘任务统计。不得让 AI 直接写入购物清单，也不得创建与 TaskList / Task 同义的食材待办类型。
- 菜谱内容、本周菜单、饮食档案与收藏均已落库并走契约接口。菜谱是平台只读内容（不带 user_id、不受 RLS）；后三者是用户数据，各自受行级安全约束。
- 本周从哪天开始由服务端按用户的周起始日偏好与时区计算，客户端不自行推导。菜单按真实日期而不是“周几”存储：跨周与跨时区时“周三”是哪天并不唯一。
- 菜单整周一次性提交并覆盖，带版本号判并发冲突；AI 生成的预览只留在客户端，用户点过“确认食谱”才写入。
- 身体数据属于高敏信息，只接受用户自己填写与修改，不接受任何推断；能力层没有登记对应 Capability。
- 平台菜谱已接入确认授权的内容；仍须保留来源、图片权利、授权范围和版本信息——`source_name`、`license`、`content_version` 是 NOT NULL，且没有 `image_credit` 就不允许挂 `image_url`。
- 页面至少覆盖首次未填写问卷、无菜单、加载骨架、搜索无结果、推荐失败、离线缓存、过敏冲突、菜单版本冲突和保存成功状态。离线时可以查看已缓存菜单与详情，但不得伪装成已经完成新的 AI 推荐。

### 8.2.3 专注场景（番茄钟）

- 番茄钟入口进入独立专注页，第一版支持番茄倒计时和正向计时。准备页以计时器为视觉中心，允许关联一个 Today Task 或输入一次性临时事项；不得复制 Task 类型或把临时事项自动保存为 Task。
- 番茄倒计时提供 25／45／60 分钟和 5—120 分钟自定义时长；正向计时从 0 开始。进行中必须支持暂停、继续和结束确认，返回键与顶部结束操作遵守同一确认规则。
- 进行中页面不得显示全局底栏或 AI 悬浮入口。用户可以暂存本次突然想到的文字，但内容只属于当前本地会话状态，不自动创建 Note、Task 或 Capture。
- 番茄倒计时完成后可以开始默认 5 分钟休息，也可以跳过；休息支持暂停、延长 5 分钟和跳过。当前不实现后台通知、应用屏蔽、严格模式、白噪音和每 4 轮长休息策略，不得用静态控件伪装这些能力已经可用。
- 保存前必须展示实际专注时长和关联任务，并让用户确认任务是否完成；专注状态评价为可选。只有用户点击“保存专注记录”后才通过生成 Client 写入内置 `focus` Tracker 的正式 Record，并刷新今日与近七天统计。
- 专注 Record 与 Task 状态是两份独立事实。选择“标记任务完成”时必须另行调用正式 Task 更新接口并保留确认，不能把完成状态塞进 Record 或只改本地展示；当前基线尚未完成这一步，详见 [实现状态](./实现状态.md)。前端 `FocusRecord` 只是展示模型，不得提升为网络 DTO。
- 记录页至少展示今日、近 7 天总时长与次数，以及按完成时间倒序的记录列表；空状态不得展示伪造效率分数或趋势。核心触控区域不小于 44×44 dp，计时状态必须有可读文字，不只使用颜色或动画表达。

### 8.2.4 记账场景

- 记账入口首屏直接展示当月支出、收入、结余、拍照／手动记账操作和最近账单，不显示通用功能介绍或提醒横幅。月预算只有在正式预算字段、修改规则和历史口径进入契约后才可展示。
- 拍照记账必须支持“拍摄小票”和“选择账单截图”两种来源。识别结果先生成可编辑候选，至少包含金额、商家或备注、收支分类、交易时间和支付方式；只有用户明确确认后才可保存。取消、识别失败、金额无效和重复候选不得生成正式 Record。
- 手动记账支持收入／支出切换、正数金额、分类和可选备注；分类、账户和时间需要有确定默认值并允许修改。金额输入与保存操作触控区域不小于 44×44 dp。
- 月度报告第一阶段至少展示收入、支出、结余、周趋势和分类占比。预算执行与上月同期变化只有在正式预算事实和完整可比历史存在时才显示。统计结果由确定性代码计算；AI 只能在统计结果上生成待确认建议，不能修改预算或自动创建任务。
- 手工记账和用户确认后的识别结果写入内置 `ledger` Tracker 的正式 Record，月度概览与列表读取同一份服务端数据。拍照／截图入口复用媒体上传、Capture Candidate、重复检测和用户确认链路；客户端不得再生成模拟商家、金额、支付方式或统计洞察。前端 `LedgerEntry` 只是展示模型，不得提升为网络 DTO。
- 页面至少覆盖默认、手动展开、图片来源选择、识别中、识别结果确认、识别失败、保存成功、空账单和无月报数据状态。照片与截图不得进入日志、埋点或测试快照。

### 8.2.5 重要日场景

- 重要日入口首屏使用“即将到来”展示今天或未来最近发生的重要日，已过期条目不得占用该位置。“更多重要日”只展示其余未来条目；已过期且不重复的日期仍保留可查，但必须单独放入“已过期”分区。今天和未来条目按发生日期升序，已过期条目按最近过期优先；各分区同时显示名称、日期、重复语义、类型图标和剩余时间，页面不显示通用功能介绍或提醒横幅。
- 导航栏右侧必须提供标准“＋”图标新增操作，默认透明、按下时显示品牌浅色反馈，不在内容标题旁放置大号胶囊按钮。新增面板支持生日、纪念日、到期日和其他四种交互预设，以及名称、公历日期、每年重复和提醒选择；公历日期使用年、月、日三列选择，切换年月时按闰年和当月天数自动修正日期；核心操作触控区域不小于 44×44 dp。
- 四种预设不新增领域类型，正式保存全部映射为 `event_kind=important_date` 的全天 Event。生日和纪念日默认 `recurrence=yearly`，到期日和其他默认 `recurrence=none`；用户可以修改，但不得提供日／周／月重复选项。
- 全天提醒必须写明当地触发时刻，当前交互默认 09:00；前端可组合选择提前 7 天、提前 1 天和当天提醒。提醒保存、时区换算与年度投影接入正式数据后由服务端确定性逻辑处理，App 不自行推断权威发生时间。
- 点击条目打开统一详情，至少展示类型、下一次发生日期、重复规则和提醒摘要，并提供“编辑重要日”和删除；详情不再提供“在日历中查看”快捷入口。已过期条目除状态文案和一次性条目的“标记已处理”外，与其他重要日使用同一信息结构和编辑入口。2 月 29 日在非闰年投影到 2 月 28 日，详情保留原始月日；删除必须明确说明会同时从重要日与日历中移除，并经过用户确认。
- “已过期”和“已处理”是两份独立事实：`days_until < 0` 只表示一次性日期早于用户当地今天，由服务端确定性计算，不代表用户已经处理；只有用户明确点击“标记已处理”或确认同义 AI Proposal 后，服务端才写入 `important_date_handled_at`。一次性重要日无论是否已到期都可标记已处理；年度重复重要日不提供永久处理状态。
- 已处理的一次性重要日不再进入重要日首页、Today 或待提醒列表，但 Event 仍作为历史事实保留在日历和通用查询中，并显示“已处理”；标记后提供短时撤销。编辑日期或把条目改为年度重复时自动清除已处理状态，使它重新进入活动读模型。删除与已处理不同：删除走 Event 软删除并从所有普通读取入口消失。
- 当前列表、新增、编辑、处理和删除均接正式 API，统一保存为 `event_kind=important_date` 的全天 Event；`important_date_kind`、年度重复、当地提醒、处理状态、2 月 29 日投影和排序均由正式契约与 Go Domain 处理。AI 可通过带 `expected_version` 的 `events.propose_update` 建议更新日期或标记已处理，但确认前不写正式 Event。第一版只支持公历，不接入系统联系人、设备日历、通知权限或共享能力；服务端提醒规则不等于设备推送已送达。

### 8.2.6 购物场景

- 购物入口首屏直接展示待购买进度和分类清单，不显示通用介绍横幅、内联快速输入框或页面底部的说明性文案。导航栏右上角提供不小于 44dp 的标准“＋”入口。
- 点击“＋”打开底部商品面板，只要求名称、数量／规格和可选备注。数量／规格使用单个自由文本字段，不维护独立单位；名称或数量／规格为空时保存按钮禁用。品类不在前端新增表单中维护，正式结果由服务端确定性分类或经用户确认的 AI 分类候选返回，并允许后续重新归类。当前本地关键词分类只用于模拟服务端返回，无法匹配时归入“其他”，不得直接提升为网络或 AI 契约。
- 待购买商品按服务端返回的蔬菜水果、肉蛋奶、主食调味、饮品冲调和其他分组，每项至少显示名称、数量／规格和可选食谱来源。商品行左侧勾选只切换购买状态，点击正文打开同一底部面板编辑。勾选后商品移入“已买到”，该区域支持折叠、展开、编辑和移回，不能让完成项无反馈地消失。
- 状态区显示待购买数、已完成数和确定性进度。“从食谱添加”直接进入当天食材确认页；合并重复食材、排除不购买项和最终创建 TaskList / Task 仍须经过用户确认。
- 未购买商品持续展示；商品勾选完成后在用户当前时区当天保留在“已买到”，次日自动停止展示。记录仍保留，不通过定时删除实现。
- 当前购物清单已复用正式 `list_kind=shopping` 的 TaskList／Task，数量／规格、服务端品类、备注和食谱来源均已进入契约；新增、编辑与勾选使用生成 Client。第一版不实现多人实时共享、超市货架顺序、价格预算、优惠内容、常购推荐或线上下单。前端 `ShoppingListItem` 只是视图模型，不得提升为第二套网络 DTO。

### 8.2.7 行程场景

- 行程使用独立 `/trips`、`/trips/new`、`/trips/new-item` 和 `/trips/[id]` 路由。详情提供“安排、预订、清单”三个同层级页内视图。
- 新建行程支持手工表单与“AI 创建”。开始和结束日期使用同一个范围控件，结束日期不得早于开始日期。两条路径最终都通过正式 Project Command 创建 `project_kind=trip` 的 Project，不创建 Trip Object。
- Project 描述第一行保存目的地，余下内容保存注意事项；总览只展示目的地，详情在有内容时展示注意事项。该约定不得在客户端之外复制为新的网络 Schema。
- 详情右上角“＋”新增交通、住宿或活动。交通必须包含方式、出发地、到达地、出发时间和到达时间；住宿必须包含名称、地点、入住时间和离店时间；活动必须包含名称与起止时间。
- Event 的 `itinerary_details` 保存安排类型、交通方式、路线、班次、座位、预订状态和票据媒体 ID。“预订”只收录明确标记为交通或住宿的 Event，不根据地点字段猜测。
- “AI 识别票据”复用 Capture，携带目标行程上下文；模型输出 `capture-parse@v5` 候选并保留图片来源、澄清回答来源、更新目标和关系引用，用户确认后由 Go Domain 校验项目归属、版本、时间和媒体引用再写入。

新增用户功能必须在同一功能交付中提供对应的 AI 入口和受控能力，至少覆盖最核心的理解、查询、创建、更新或辅助流程。AI 写入始终遵循“结构化候选／建议 → 用户确认 → Go Domain Command”，并保留不依赖模型的手工路径；受安全、合规或事实来源限制的能力必须在规格中明确写出边界，不能静默遗漏。

## 8.3 Today Tasks 收录规则

未完成且未取消的 Task 满足任一条件时进入 Today：

- `focus_date` 是今天。
- `scheduled_start_at` 是今天。
- `due_date` 不晚于今天。
- `due_at` 不晚于今天结束时间。
- 用户在清单或 Task 详情中执行“加入今天”。

未设置日期且未加入今天的普通 Task 不自动混入 Today。

首页默认只渲染排序后的前 4 项 Task；存在更多 Task 时显示剩余数量和展开按钮。展开只改变客户端可见数量，不改变 Today 收录、排序或 Task 字段；展开后可以收起。

Today Task 列表末尾和空状态不提供局部“添加任务”。手动输入统一从底栏中央 `＋ Capture` 进入；用户在确定性 Task 表单中显式打开“加入今天”时写入当天 `focus_date`，不得自动写入 `due_date` 或 `due_at`。

## 8.4 Today Tasks 排序规则

先按分组排序：

1. 已逾期。
2. 今天截止。
3. 今天有计划时间。
4. 手动加入今天。

同组内依次按：

1. 优先级：`high`、`normal`、`low`。
2. 截止日期／时间或计划开始时间更早者优先；同日内，有明确 `due_at` 的任务按时刻排序，只有 `due_date` 的任务排在其后。
3. 创建时间更早者优先。

一个 Task 同时符合多个分组时，只进入顺序最靠前的分组。

AI 可以给出调整顺序的建议，但不允许用不可解释的模型排序覆盖上述基础顺序。

## 8.5 Task 快捷操作

Today 中每个 Task 支持：

- 完成。
- 开始处理。
- 延期到指定日期。
- 从今天移除。
- 修改。
- 进入所属 Project。

“从今天移除”只清除 `focus_date`；如果任务因今天截止或今天已排期而出现，必须提示用户同时修改对应时间后才能移除。

“延期到指定日期”遵循原截止语义：原来是 `due_date` 时只改日期；原来是 `due_at` 时默认保留当地时刻并允许修改；原来没有截止信息时创建 `due_date`。

## 8.6 页面状态

- 首次加载显示骨架状态，不显示旧日期数据冒充当天数据。
- 单个场景暂不可用时保留入口位置并明确提示“暂不可用”，不得跳转到空白页面或改变其他入口顺序。
- 无 Task 时展示空状态；输入统一由底栏中央 `＋ Capture` 到达。
- 没有有效 Daily Brief 时不渲染“今日提醒”分区，也不显示空卡片或占位文案。
- 拉取失败时保留最近一次数据并标注“可能不是最新”，同时提供重试。
- 跨过零点或用户切换时区后，页面必须重新计算“今天”。

# 9. F-07 Task

## 9.1 创建与编辑

Task 可以从以下入口创建：

- Capture 对话内确认。
- 全局 Capture 面板内的确定性手动入口。
- 清单首页或某个 TaskList。
- Project 详情。

手动新建表单必须显式展示标题、备注、加入今天、优先级、截止、提醒和 TaskList 等可编辑字段。首屏使用分组属性行，不使用大面积实心品牌色表示普通选中态；截止日期、优先级和清单从底部选择面板按需展开，当前选项使用浅色背景和勾选图标表达。未设置截止日期时隐藏到期提醒；设置截止日期并打开提醒后显示可点击的“提醒时间”，初始值沿用用户偏好，用户选择的具体时间随 Reminder 保存。入口上下文只能形成表单预选值：具体 TaskList 预选其 `list_id`，“随时可做”和全局手动入口不预设日期。保存统一调用正式 Task 创建 Command；AI 创建继续通过 Capture Candidate、用户确认和同一 Domain Command，不新增第二套写入规则。

用户必须能够编辑第 2.2 节定义的所有非系统字段。

校验规则：

- 标题不能为空。
- 计划结束时间必须晚于计划开始时间。
- `due_at` 早于计划结束时间，或计划结束日期晚于 `due_date` 时，显示冲突警告，但允许用户确认保存。
- 将 Task 标记完成时写入 `completed_at`。

## 9.2 AI 拆分

用户在 Assistant 中请求拆分当前 Task 后：

1. AI 根据当前 Task 标题、描述和所属 Project 生成子任务候选。
2. 候选默认不保存。
3. 用户可以编辑、删除、补充和选择候选。
4. 用户确认后批量创建 Task，并与原 Task 建立 `related_to` 关系。
5. AI 不自动把原 Task 标记完成。

## 9.3 智能安排

用户在 Assistant 中请求安排当前 Task；Task 详情不提供内嵌 AI 操作入口。

Scheduler 使用：

- Task 截止日期或截止时间。
- 预计耗时。
- 产品内部 Event 和已有 Task 计划时间。
- 用户工作时间和周末偏好。

输出必须包含：

- 首选时间段。
- 推荐理由。
- 最多 3 个备选时间段。
- 无可用时间时的明确说明。

规则：

- 推荐时间不得与已有 Event 或已计划 Task 重叠。
- 默认只推荐工作时间内的时段。
- 只有 `due_date` 时，以该日期的用户工作结束时间作为排期约束，但不得把这一计算时刻回写为 `due_at`。
- 截止前没有完整空档时，可以提出拆分建议，但不得自动拆分。
- 用户确认后才写入 `scheduled_start_at` 和 `scheduled_end_at`。

# 10. F-08 Event

## 10.1 创建与编辑

Event 可以从 Capture 对话内确认、Today 和 Project 详情创建。

必须支持：

- 编辑标题、开始时间、结束时间、全天状态、地点和参与人。
- 设置、修改和删除提醒。
- 关联或移出 Project。
- 添加说明。
- 删除 Event。

冲突规则：

- 与已有 Event 重叠时显示冲突提示，但不强制禁止保存。
- 定时 Event 的 `end_at <= start_at`，或全天 Event 的 `end_date < start_date` 时禁止保存。
- 从定时 Event 切换为全天 Event 时，清除具体时刻并要求确认 `start_date/end_date`；反向切换时清除全天日期字段并要求确认 `start_at`。
- 修改时区时必须展示转换后的当地时间，避免静默改变实际时刻。

## 10.2 会前准备

Event 开始前可以展示：

- 与 Event 有 `requires` 关系的未完成 Task。
- 同一 Project 下近期更新的 Note。
- 尚未确认的关键字段，例如地点为空。

每条信息必须可点击打开来源 Object。没有来源时不生成该条内容。

# 11. F-09 Project

## 11.1 计划中的项目入口

从“计划 → 清单详情 → 项目筛选”进入，默认展示“全部项目、进行中、已暂停、已归档”。选择状态后展示该状态下的具体 Project：

- 名称。
- 状态。
- 目标日期。
- 任务进度。
- 最近一个待办或 Event。

排序规则：

1. 有逾期 Task 或目标日期风险的 Project。
2. 目标日期更近的 Project。
3. 最近更新时间更近的 Project。

完成的 Project 自动进入归档，不提供“已完成”筛选。轻点具体 Project 筛选当前任务列表，长按进入详情。

不得提供绕过 Capture 的手工“新建 Project”表单。新目标必须从统一 Capture 进入：

1. 用户只描述目标，不先选择 Task 或 Project。
2. AI 判断是否需要多个步骤和持续推进；单步事项生成 Task Candidate，多步骤目标才生成 Project Candidate。
3. Project Candidate 展示判断理由、名称、日期和初始 Task 建议；名称必填，`target_date` 早于 `start_date` 时禁止确认。
4. 用户确认后才创建 Project，默认状态为 `active`；关闭、取消或未选择候选时不得创建空 Project。

## 11.2 Project 详情

页面包含：

- Overview：描述、状态、日期和进度。
- Next：接下来最重要的 1～3 个未完成 Task。
- Timeline：按时间排列 Event 和有时间的 Task。
- Objects：全部关联 Task、Event、Note 和 Record。
- Data：Project 下的 Record。

Project 内的“新增内容”打开统一 Capture，并把当前 `project_id` 作为可见的预选上下文；用户仍不先选 Task、Event 或 Note。AI 生成候选后，对话内确认区展示当前 Project 归属，用户可以改为其他 Project 或不关联，确认后再写入最终 `project_id`。

## 11.3 Next 规则

系统先使用确定性规则选择 Next：

1. 逾期 Task。
2. 今天或最近 7 天内截止的 Task。
3. 高优先级 Task。
4. 创建时间最早的“随时可做” Task。

最多显示 3 项。AI 可以在解释原因后建议替换，但不静默改变 Task 字段。

## 11.4 Project Summary

摘要最多包含：

- 当前已完成事项。
- 最近需要处理的事项。
- 明确可计算的风险。
- 一个可执行建议。

风险必须来源于以下可验证条件：

- Task 已逾期。
- 目标日期临近且存在未完成 Task。
- 近期 Event 缺少地点或关联准备任务未完成。
- 用户在已确认的 Task 或 Note 中明确记录了仍待业务确认的事项。

# 12. F-10 Note

笔记是一级正式内容模块，用于保存当前不要求执行、也不要求按固定字段重复统计的信息。笔记首页必须支持：

- 使用一个连续内容流；数据仍按置顶优先、最近更新时间排序，但首页不显示“置顶”“最近更新”等分区标题。
- 首页常驻标签筛选；Project 归属在 Note 详情中查看和调整，不在首页形成第二套分类。
- 标题与正文全文搜索。
- 默认使用无描边、无分割线的摘要卡片流，卡片显示标签、更新时间、标题、正文摘要和附件标记。
- 从 Capture 对话内确认、笔记首页、Project 详情和其他 Object 的“保存为笔记”动作创建。

Note 支持：

- 创建、查看、编辑和删除。
- 正文使用 `NoteContent` 判别联合，每篇只保存一种权威格式。当前普通笔记编辑器创建 `plain_text`，心情日记通过专用接口创建 `blocks_v1`；普通 Note 接口不能伪造 `mood_journal`，也不能在 PATCH 时隐式转换正文格式。
- 列表摘要、搜索、转换 Task 和 AI 输入读取服务端随正文事务生成的只读纯文本投影。客户端不能提交该投影，转换 Task 时也不得把富文本 JSON 放进 Task 描述。
- 新建时可对已有正文执行一次 AI 润色；标题为空时同时生成标题，已有标题不改写。润色结果只回填编辑器，用户检查并保存后才写入 Note。
- 添加图片和受支持附件；附件只作为笔记内容保存，不擅自生成 Task 或 Record。
- 添加标签、置顶和取消置顶。
- 关联或移出 Project。
- 转换为 Task。
- 从笔记首页、搜索结果和 Project 中打开。
- 查看实际来源；可能是 Capture、原 Note／Task 或 AI Action。

转换为 Task 时：

- 使用 Note 标题作为 Task 标题候选。
- Note 内容作为 Task 描述候选。
- 用户确认后创建新 Task。
- 原 Note 默认保留，并与 Task 建立 `related_to`；用户可以选择删除原 Note。

Note 中出现日期、金额或数字时不自动改变类型；只有用户明确要求执行、记录到 Tracker，或在对话内确认区主动改变候选类型时，才生成 Task、Event 或 Record。

普通 Note 的一键润色必须保留事实、数字、日期、单位和不确定语气，不补充原文没有的信息；它只支持 `plain_text`，不得接收 `blocks_v1`。心情日记使用独立的结构化排版润色契约和 API，不复用纯文本结果。两条链路处理中原文都保持可见但暂时只读，完成后可以撤销；失败不得清空或覆盖草稿，采用结果保存时必须带本次 AI Action 来源引用。

# 13. F-11 Tracker / Record

“打卡”是 Data 的用户可见名称和一级入口；内部路由、领域名、API 与类型继续使用稳定的 Data、Tracker 和 Record。该模块只承载可复用 Schema 和满足 Schema 的结构化 Record，不作为普通笔记或附件仓库。打卡首页只展示没有独立场景页面的自定义 Tracker；运动、专注和记账继续复用 Tracker／Record 作为数据底座，但只在各自模块展示和录入。首页展示今天按频率需要记录的项目、活跃自定义 Tracker、最近值、变化和归档筛选。

## 13.1 创建 Tracker

入口：打卡首页的“新建记录”。

支持两种方式：

- 用户手动填写名称和字段。
- 用户用自然语言描述，由 AI 生成 Schema 候选。

AI 示例：

```text
输入：帮我记录每场直播的观看人数、成交额和转化率。

候选 Tracker：直播数据
- 观看人数：Number
- 成交额：Currency / CNY
- 转化率：Percentage
```

保存前用户必须能修改名称、字段名、类型、单位、必填状态和频率。频率支持不定期、每天和每周指定星期；不定期 Tracker 不进入“今日待打卡”。

## 13.2 写入 Record

Record 可以从以下入口创建：

- Tracker 详情。
- Today Records。
- Capture 对话内确认。
- 运动、专注和记账的专用场景；这些内置 Tracker 不在打卡首页重复展示。

匹配规则：

- 用户明确说出 Tracker 名称时，优先匹配该 Tracker。
- 只有一个 Tracker 的字段与输入完整匹配时，可以生成该 Tracker 的 Record 候选。
- 存在多个可能 Tracker 时必须让用户选择。
- “今天 72.3”不能在缺乏上下文时自动猜测是体重。
- 字段类型不匹配时禁止保存，并指出需要修正的字段。

## 13.3 Tracker 详情

展示：

- 最近 Record。
- 基础统计：记录次数、最近值、与上一条的变化。
- 趋势图和周、月周期统计。
- 按发生时间倒序排列的 Record 列表。

Tracker 的 Schema、名称和频率只在管理编辑流程中展示和修改，普通详情不重复展示配置字段。

AI Summary 规则：

- 少于 2 条有效 Record 时不输出趋势结论。
- 只能描述数据中可以计算的变化。
- 用户询问原因但数据不足时，必须说明无法确认原因，并建议补充哪些字段。

## 13.4 Schema 变更

- 新增可选字段不影响历史 Record。
- 删除已有数据的字段时必须二次确认；历史值保留但默认不展示。
- 修改字段类型可能导致历史值不兼容，MVP 不允许直接修改；应新建字段或新 Tracker。
- 归档 Tracker 后不再出现在 Today Records，但历史 Record 可查看和搜索。

# 14. F-12 Search

## 14.1 基础搜索

搜索范围：Task、Event、Project、Note、Tracker 和 Record。

支持匹配：

- 标题。
- 描述或正文。
- Project 名称。
- Event 地点和参与人文本。
- Tracker 字段及 Record 文本值。

结果按相关度优先，其次按最近更新时间排序，并按 Object 类型分组。

## 14.2 自然语言搜索

支持：

- “上海出差还有哪些没做？”
- “我上次和王总聊了什么？”
- “最近一个月哪场直播成交最高？”
- “我今天有什么可以推迟？”

回答规则：

- 每一个事实性结论必须附带至少一个来源 Object。
- 来源可点击进入详情页。
- 没有足够数据时直接说明，不能用常识补充用户事实。
- 涉及修改的查询只返回建议，不直接改变 Object。
- 查询时间范围必须按用户当前时区解释，并在回答中显示实际日期范围。

## 14.3 无结果与错误

- 无结果时显示已搜索的范围，并提供修改关键词或新建 Capture 的入口。
- 自然语言回答失败时仍展示基础关键词搜索结果。
- 已删除 Object 默认不参与搜索。

# 15. F-13 AI 计划与复盘

## 15.1 Daily Brief

每天首次打开 Today 时生成或读取当天摘要，最多 3 条。

允许使用的事实：

- 当天 Event 时间分布。
- 逾期和当天截止 Task。
- Project 目标日期及未完成 Task。
- 活跃 Tracker 当天是否缺少 Record。

规则：

- 每条结论必须附带来源。
- 同一事实当天不重复提醒。
- 数据变化后允许用户手动刷新。
- 没有值得提醒的事项时不渲染首页“今日提醒”分区，不生成空泛建议。

## 15.2 Weekly Review

默认按用户所在时区统计上一个自然周（周一 00:00 至周日 23:59:59）。

输出包括：

1. 结构化小结：短标题、一到两句摘要和最多两条指标重点。
2. 数据概览：完成 Task、延期 Task、Event、活跃 Project、Record 数；仅在尚未生成小结时展示完整指标。
3. AI 观察：最多 3 条。
4. 下周建议：最多 3 条。

规则：

- 每个指标必须有固定计算口径。
- 每条观察和建议必须附带相关 Object 或 Record。
- 用户可以查看统计日期范围。
- 数据不足时省略对应观察，不用通用建议填满页面。
- 指标与环比变化均为空时不调用模型，直接返回空周状态。
- AI 只返回结构化 JSON，不输出 Markdown、HTML 或界面样式。
- Review 生成后保留快照；后续数据修改时标注“数据已变化”，由用户选择重新生成。

## 15.3 AI 建议的统一规则

- 建议与事实必须在视觉和文案上明确区分。
- AI 建议默认不修改数据。
- 接受建议前必须展示将要修改的 Object 和字段。
- 用户拒绝建议不影响原 Object。
- 接受和拒绝均记录为产品埋点，用于评估质量，不作为不可见的永久用户记忆。

# 16. F-14 通知

## 16.1 通知类型

| 类型 | 触发条件 |
|---|---|
| Event Reminder | Event 设置了提醒且到达触发时间 |
| Task Due | Task 设置了截止提醒且尚未完成或取消 |
| Daily Brief | 用户开启且当天存在有效 Brief |
| Project Risk | 用户开启且出现新的可验证风险 |
| Weekly Review | 新的周报已生成 |

明确触发口径：

- Daily Brief 开启时，系统在用户当地 `workday_start_local` 尝试生成当天 Brief；用户更早首次打开 Today 时也可提前生成。只有存在有效 Brief 才创建通知，同一当地日期最多一次。
- Weekly Review 开启时，系统在用户当地周一 `workday_start_local` 生成上一个自然周快照；成功后通知，同一统计周期最多一次。
- Project Risk 在 Project、关联 Task 或 Event 的相关字段变化后按第 11.4 节确定性条件重算；只有新出现或事实版本发生实质变化的风险才通知。风险解除后再次出现可视为新触发，但不得因后台重试重复通知。
- 后台周期扫描只用于补偿漏调度；它与页面主动生成必须复用同一幂等生成记录和通知触发键。

## 16.2 通用规则

- 只在用户首次启用提醒时申请系统通知权限。
- 权限被拒绝后，产品内提醒仍可展示。
- 同一 Object、同一触发条件只发送一次通知。
- Task 完成、取消或删除后，未发送提醒必须取消。
- Event 或 Task 时间修改后，旧提醒必须取消并按新时间重建。
- 点击通知必须打开对应 Object 或 Review。
- 时区变化时按照 Object 的时区语义重新计算，避免重复或漏发。
- 默认不发送营销通知。

# 17. F-15 操作记录与撤销

## 17.1 Activity Log

记录以下操作：

- AI 批量创建 Object。
- AI 建议被接受或拒绝。
- Tracker 创建、修改、归档、删除和恢复。
- Object 创建、修改、删除和恢复。
- Relation 创建和删除。

每条记录至少显示：发生时间、执行者、动作、影响实体和操作入口。存在来源时显示 Capture、Object 或 AI Action；用户手工操作允许没有来源实体，但必须标记“用户手动操作”。涉及修改时还必须保存可用于撤销的修改前后版本；界面可以只展示用户易读的字段差异。

## 17.2 即时撤销

- Capture 对话内确认批量保存成功后，显示 10 秒即时撤销入口。
- 撤销必须把本批次新建的 Tracker、Object 和 Relation 一并软删除，并把本批次更新的已有实体和 Relation 恢复到操作前版本。
- 如果用户已经修改了本批次中的任一 Object，再执行撤销时必须提示这些后续修改也会被移除，并要求二次确认。
- Activity Log 用于追溯，不提供任意历史时点回滚。
- 普通编辑错误通过再次编辑修正；普通删除不可撤销，因此删除前要确认。

# 18. F-16 我的

“我的”不占用底部一级导航。用户只从“首页”左上角小头像进入“我的”，在同一一级页面查看和进入使用习惯、AI、隐私和账号管理；不再增加“全部设置”中转页。其他一级页面不重复显示头像。Weekly Review 统一从首页“复盘”场景进入，“我的”不重复提供“本周回顾”摘要。

资料栏显示头像、显示名称和脱敏手机号。点击资料栏在当前页打开短任务底部面板，不新增资料导航页；当前版本头像由显示名称首字生成，修改显示名称会同步更新头像。照片头像必须等用户头像与受控媒体之间的正式引用、读取和删除契约完成后再开放，不得把短期签名 URL 或任意客户端 URL 保存为头像。

## 18.1 使用习惯

用户可以查看和修改：

- 工作日开始与结束时间。
- 是否周末工作。
- 默认 Event 提醒时间。
- 默认 Task 预计耗时。
- AI Scheduler 是否允许推荐工作时间外的时段。

## 18.2 AI 设置

用户可以分别关闭：

- Daily Brief。
- Weekly Review。
- Project Summary。
- Data Summary。
- 用户偏好学习。

关闭某项分析后，不再生成新的对应结果；已有结果仍可查看和删除。

用户偏好学习产生的长期偏好必须：

- 在“我的”中可查看。
- 标明来源是用户设置还是行为推断。
- 支持逐条修改和删除。
- 删除后不再继续用于推荐，除非用户再次设置或允许重新学习。
- 行为或对话推断只能先形成可查看的偏好建议；用户确认或编辑后才成为可用于推荐的 active 长期偏好。
- 单次行为、一次性限制和未经用户确认的模型推断不得静默进入长期偏好。

## 18.3 隐私与账号

必须提供：

- 查看公开 H5《隐私政策》《用户协议》、个人信息收集清单、第三方信息共享清单和帮助联系方式。
- 查看并删除原始 Capture。
- 删除单个 Object。
- 查看和删除 AI 长期偏好。
- 删除账号及账号内全部数据。
- Capture 确认或放弃后自动删除原始录音的开关。
- Capture 确认或放弃后自动删除原始图片的开关。

规则：

- 删除账号属于高影响操作，必须二次确认并再次验证身份。
- 删除重新认证使用独立验证码用途和 10 分钟单用途凭证；受理后账号立即变为 `deletion_pending`，全部 Refresh Token 失效，既有 Access Token 不能再访问普通用户接口。
- 客户端在 reauth 有效期内安全保存同一 reauth token 与删除幂等键；受理响应丢失时只允许重放完全相同的删除请求，取得 `deletion_request_id` 与状态凭证后立即清除该短期记录。
- 删除状态由不含身份与业务内容的独立镜像提供，使用 `deletion_request_id` 与 `Deletion-Status-Token` 查询；状态凭证不能用于任何普通 API。
- 更换绑定手机号要**同时验证旧号与新号**。账号就是手机号（登录＝手机号＋验证码），
  只验新号的话一个被劫持的会话就能永久接管账号，真正的机主再也登不进来。
  换绑用的验证码与登录码用途分开，登录码不能拿来换绑。
  换绑成功后其他设备上的登录失效，当前设备不受影响。
- 删除原始 Capture 不删除已经确认创建或更新的 Tracker、Object 和 Relation，但其来源入口显示“原始内容已删除”。
- 删除 Object 不反向删除原始 Capture。
- 用户删除单个原始音频或图片时，只删除该输入项的原始资产；已生成的转写、OCR 继续保留并明确标注“原始资产已删除”，已经确认的 Object 不受影响。
- 开启自动删除开关后：Capture `confirmed` 或 `discarded` 时删除对应原始资产；为追溯保留用户确认过的文字、转写、OCR 结果和来源类型，不保留原图或录音。
- `draft`、`awaiting_instruction`、`needs_confirmation`、`partially_failed` 和 `failed` 的 Capture 自最后更新时间起保留 30 天；届时变为 `expired` 并删除原始音频和图片。处理前 3 天向用户显示清理提示。
- 自动删除关闭时，原始资产随 Capture 保留，直到用户主动删除 Capture、删除账号或适用的数据保留期限到期。
- 首次提交音频或图片给 AI 前，必须展示处理目的和隐私说明，并提供“同意并继续”与“返回编辑”。用户拒绝时不上传、不解析，返回编辑器并保留可移除或替换的本地输入；文字输入仍可继续提交。
- 普通删除的 Object 和 Project 立即从各自的列表中消失，不提供「最近删除」回收站。

账号区域直接显示脱敏绑定手机号并提供更换入口；更换手机号仍是独立的高安全操作流程。退出登录位于“我的”底部危险操作区，确认后服务端作废会话并清理本地会话与全部用户缓存。没有正式契约的第三方账号绑定、登录设备和安全中心不展示占位入口。

公开法律文本与帮助内容采用 H5，实际隐私控制、账号验证和删除操作保持原生并调用正式领域契约。H5 与原生边界、固定 URL、账号删除 Web 要求和开发提醒门禁见《H5 与公开页面边界》。

# 19. 全局功能规则

## 19.1 时间与时区

- 有具体时刻的字段在服务端保存绝对时间及原始时区，界面按用户当前时区展示。
- Task `due_date` 和全天 Event 保存当地日期及原始时区语义，不转换成虚构的零点或 23:59，避免跨时区后日期漂移。
- 全天 Event 是浮动日历日期：用户切换时区后仍显示在其 `start_date/end_date` 标记的日期；Today 用当前正在查看的日历日期直接比较。Task `due_date` 则按第 2.2 节定义的 `due_timezone` 判断是否到期或逾期。
- 所有“今天、本周、下周”都以用户执行操作时的时区为准。
- 普通用户不手工维护 IANA 时区。App 登录、启动和回到前台时读取系统当前时区；与用户资料不一致时自动同步并刷新日期相关查询。同步失败保留服务端旧值并在下次前台恢复时重试，不阻塞查看和手工操作。只有未来出现“固定常驻时区”等明确高级场景时才提供高级设置。
- Object 涉及其他时区时，详情页同时显示事件时区和本地时间。
- MVP 暂不支持重复 Task 和普通日程；用户需要逐个创建。唯一例外是 `important_date` 的按年重复，用于生日、纪念日等稀疏日期。用户输入“每天”“每周”等其他重复规则时必须明确提示限制。

## 19.2 加载、空状态和失败

每个主页面必须具有：

- 首次加载状态。
- 空状态和明确下一步入口。
- 网络失败状态和重试入口。
- 无权限状态及解决办法。
- 部分数据不可用时的降级说明。

AI 失败不得阻止用户手动创建、编辑或查看已有 Object。

## 19.3 数据一致性

- 所有写操作必须防止重复提交。
- 批量确认要么全部成功，要么全部失败。
- 删除 Project 前必须让用户选择：仅移出关联 Object，或同时删除关联 Object。
- 默认选择“仅删除 Project，并把关联 Object 移入未归属状态”。
- 已删除、已完成和已取消内容不得继续触发未来通知。

## 19.4 AI 可解释与可追溯

- AI 创建或更新的 Tracker、Object 和 Relation 必须通过 `provenance_refs[]` 回到实际来源 Capture、Object 或 AI Action；不得为非 Capture 功能伪造 Capture 来源。
- AI 摘要中的结论必须能回到来源 Object 或 Record。
- AI 推断值必须与用户明确输入的值区分。
- 用户修正字段时记录“原值、修正值和字段”，用于质量评估。
- 不得向用户展示内部思维过程；只展示简短、可验证的推荐理由。

## 19.5 功能载体与远程更新

- 每个新增或重做的用户功能必须在设计阶段明确选择公开／功能型 H5、React Native 或应用商店原生版本，并在功能说明中记录原因；不能只用“少发版”作为 H5 决策依据。
- 读为主、轻交互、在线可用、无需原生权限且具有频繁更新或公开分享收益的功能，优先评估 H5。法律帮助、模板／教程、公开食谱／攻略和用户主动分享的只读报告属于候选范围。
- 依赖相机、麦克风、定位、通知、后台任务、可靠离线、高频核心状态、登录安全、隐私控制或 AI 写入确认的功能保持原生。
- H5 中的登录态和写操作继续使用正式 OpenAPI、生成 Client、运行时校验、用户隔离、幂等和版本冲突；页面刷新、断网或会话过期不得造成重复写入或虚假成功。
- 项目已按 `ADR-028` 接入 `expo-updates`，以 App 版本作为 runtime version，并固定使用隔离的测试／生产频道。只有配置正式 Expo Project 与签名 Secret、发布包含验签证书的新原生包并完成测试、灰度和回滚演练后，才视为正式能力；原生 SDK、权限、依赖或不兼容运行时变化始终走应用商店发布。
- H5、OTA 和 Feature Flag 不得用于规避应用商店审核、隐私告知或重大产品变更评审。详细矩阵与开发提醒见《H5 与公开页面边界》。

# 23. 本稿采用的确定性决策

为了让设计和研发可以直接基于同一版本工作，本稿不再保留阶段性分层，并采用以下明确决策：

1. 文字、语音、图片、图片＋文字、图片＋语音全部属于同一个 MVP。
2. Tracker / Record、AI Scheduler、Daily Brief、Weekly Review、Project Summary、自然语言搜索和系统通知全部属于 MVP。
3. 登录采用手机号和验证码；增加其他登录方式不影响本文核心功能。
4. 数据导出、「最近删除」回收站与登录设备管理**不属于本版范围**。
   删除即删除，不提供 30 天回收站；导出与设备管理留到有明确合规或用户诉求时再做。
5. 系统日历同步、通用文件解析、团队协作和外部信息源不属于 MVP。
6. 所有 AI 解析和建议结果必须先确认后保存；所有 AI 总结结论必须能回到来源。
