# 自动部署

## 部署结构

steward 复用 huahuadog 的 ECS、ACR 和 SSH 密钥，但使用独立目录、端口和 Compose 项目。

| 环境 | 触发方式 | 服务器 Secret | 目录 | 宿主端口 |
|---|---|---|---|---|
| 测试 | `main` 推送后自动部署 | `TEST_SSH_HOST` | `/opt/steward-test` | `8088` |
| 生产 | 手工输入 main 分支 commit SHA | `PROD_SSH_HOST` | `/opt/steward-prod` | `8088` |

两个 Secret 复用 huahuadog 对应的测试、生产机器。两台机器上的 steward 都使用 `8088`，不占用 huahuadog 已使用的宿主机 80 端口。

入口路由：

- `/`：移动 Web。
- `/v1/`：公共 API。
- `/admin/`：管理台。
- `/admin/v1/`：管理 API。
- `/healthz`、`/admin-healthz`：部署健康检查。

## 首次配置

### 1. ACR 与 GitHub Secrets

ACR 建立三个仓库：

- `steward-backend`
- `steward-mobile-web`
- `steward-admin-web`

GitHub 仓库配置以下 Secrets，值可复用 huahuadog：

```text
ACR_REGISTRY
ACR_PULL_REGISTRY
ACR_NAMESPACE
ACR_USERNAME
ACR_PASSWORD
TEST_SSH_HOST
PROD_SSH_HOST
SSH_KEY
ANDROID_TEST_KEYSTORE_BASE64
ANDROID_TEST_KEYSTORE_PASSWORD
```

生产服务器部署和 Android 正式发布都使用 GitHub `production` Environment；需要人工审批时，在该 Environment 配置 reviewer。Android 正式发布还会读取：

```text
ANDROID_PRODUCTION_KEYSTORE_BASE64
ANDROID_PRODUCTION_KEYSTORE_PASSWORD
```

签名别名固定为 `steward-test` 和 `steward-production`。JKS 文件的 Base64 使用单行文本保存到 Secret，原始生产签名和密码还必须离线备份。

### 2. 数据库、Redis 与 OSS

复用 huahuadog 的同一套实例，但做环境隔离：

| 环境 | PostgreSQL 数据库 | 运行账号 | 后台账号 | 迁移账号 | Redis DB | OSS 前缀 |
|---|---|---|---|---|---|---|
| 测试 | `steward_test` | `steward_t_app` | `steward_t_admin` | `steward_t_mig` | `5` | `steward/test` |
| 生产 | `steward_prod` | `steward_p_app` | `steward_p_admin` | `steward_p_mig` | `6` | `steward/prod` |

RDS 还要预建不实际登录的 ACL 账号 `steward_app`、`steward_admin`，供迁移保存公共权限定义。迁移 `00031` 会撤销它们对部署库的连接权，并把权限授给环境专属账号。RDS 私网连接使用 `sslmode=disable`。

Redis Pub/Sub 不按逻辑 DB 隔离，因此测试、生产还必须分别设置 `STEWARD_STREAM_NAMESPACE=steward-test` 和 `steward-prod`。

OSS Bucket 保持私有读写；对象物理键统一落在 `steward/` 下。Bucket CORS 允许 Web 域名的 `PUT`、`GET`、`HEAD`，并暴露 `ETag`。

跑步底图单独放在公开 CDN 前缀 `steward/maps/`，测试和生产共用版本化 PMTiles，不重复存储。Bucket 仍保持私有；CDN 对该前缀免 URL 鉴权，并开启 Range 回源、跨域响应头和一年不可变缓存。发布工具见 `tools/maps/`。用户轨迹不得写入该公开前缀。

### 3. 服务器环境文件

```bash
mkdir -p /opt/steward-test/deploy /opt/steward-prod/deploy
```

分别把模板复制到服务器并填入真实值：

```text
.env.test.example       → /opt/steward-test/.env.test
.env.production.example → /opt/steward-prod/.env.production
```

随后执行：

```bash
chmod 600 /opt/steward-test/.env.test
chmod 600 /opt/steward-prod/.env.production
```

环境文件不由 CI 上传，也不提交到 Git。管理员口令散列用 `make admin-passwd` 生成。

### 4. ALB

steward 复用 `weishen` ALB（`alb-0ta48ecgc5jvvu40pv`）。

| 环境 | 域名 | 服务器组 | 后端 | 健康检查 |
|---|---|---|---|---|
| 测试 | `test-steward.qhzhiyin.com` | `测试-steward` | 测试 ECS `8088` | `HEAD /healthz` |
| 生产 | `steward.qhzhiyin.com` | `生产-steward` | 生产 ECS `8088` | `HEAD /healthz` |

HTTPS `443` 监听按域名转发到对应服务器组；HTTP `80` 监听使用现有全局规则返回 `301` 并保留原路径和查询参数。DNS CNAME 目标为：

```text
alb-0ta48ecgc5jvvu40pv.cn-beijing.alb.aliyuncsslb.com
```

## 发布

- 测试服务器：合并或推送到 `main` 后自动运行“测试环境部署”。
- 测试 APK：本次推送包含移动端、公共 API 契约或 Android 打包配置时，在测试部署成功后生成，Actions Artifact 保留 30 天；纯后端或管理台改动不生成。手工运行测试部署时，可勾选“同时生成 Android 测试 APK”。
- 生产服务器：手工运行“生产环境部署”，只输入已在 `main` 的 commit SHA，不生成 APK。
- 生产 APK：需要发布 App 时，单独手工运行“Android 正式发布”，输入已在 `main` 的 commit SHA 和 App 版本号，产物保存到 `android-v<版本号>` GitHub Release。

正式 App 使用新接口前，先完成兼容后端的生产部署，再运行“Android 正式发布”。

测试 App 名称为“清单测试”，包名为 `com.aisteward.mobile.test`；生产 App 名称为“清单”，包名为 `com.aisteward.mobile`，两者可同时安装。每个 APK 同时生成 SHA256 文件，测试和生产使用不同的固定签名。

流水线先执行代码生成、空库迁移和 `make check`，再构建三个镜像并推送 ACR，最后通过 SSH 更新 Compose。部署使用不可变短 SHA 标签；健康检查失败会回滚到 `.last-good-tag`。

数据库迁移只向前执行。包含不兼容迁移时，自动回滚镜像不能回滚数据库，发布前必须准备单独的前滚或数据库恢复方案。

测试环境使用 `STEWARD_SMS_PROVIDER=dev` 和 6 位 `STEWARD_DEV_SMS_CODE`，不配置阿里云短信；生产环境使用 `STEWARD_SMS_PROVIDER=aliyun`，并保持 `STEWARD_DEV_SMS_CODE` 为空。阿里云 AccessKey、签名和模板只写入生产服务器环境文件，不进入 GitHub Secrets 或仓库。
