## 权威来源与冲突处理

权威性按信息维度划分，不做一条跨维度的线性排序：

| 信息维度 | 唯一权威来源 |
|---|---|
| 业务行为、范围、异常与验收 | [功能规格说明](./功能规格说明.md) |
| 页面、状态、交互与用户可见反馈 | [产品设计说明](./产品设计说明.md) |
| 模块边界、依赖方向、数据流、事务与部署形态 | [整体架构设计](./整体架构设计.md) |
| 网络路径、字段、枚举、错误码与安全声明 | `packages/contracts/openapi` |
| AI 结构化输出 | `packages/ai-contracts/schemas`；Prompt 行为另见同包 `prompts` |
| 当前数据库结构 | `apps/backend/db/migrations`；查询行为另见 `db/queries` |
| 模块局部职责与不变量 | 目标模块 README，但不得重定义上述共享契约 |
| 当前实现完成度 | [实现状态](./实现状态.md) |
| 协作流程与完成门禁 | 根 [AGENTS.md](../AGENTS.md) |

跨维度信息发生冲突时，不能用“排序更高”直接覆盖另一维度。应先确认这是实现缺口、文档陈旧还是规则变更，再在同一变更中同步修订所有受影响的权威来源、代码与测试。例如业务规则决定需要一个新状态，但状态的网络名称仍必须进入 OpenAPI，不能由架构文档或 README 直接定义。

[实现状态](./实现状态.md) 只回答“基线提交中已经实现什么”，不改变产品规则或契约。代码与权威来源不一致时，先确认预期再修正，不能用现状页反向覆盖产品决策，也不能用目标文档把未实现能力写成已经完成。

## 维护规则

### 最小元信息

正式文档顶部至少包含：文档类型、适用范围或目标读者、当前状态、更新日期。状态使用下面的稳定含义：

| 状态 | 含义 |
|---|---|
| 评审稿 | 规则仍可能变化，不能仅凭本文扩大实现范围 |
| 开发基线 | 已作为开发约束，变化需要同步影响面 |
| 已决策 | 已确认的单项架构或产品决策 |
| 维护中 | 随仓库变化持续更新的入口、现状或运维文档 |
| 历史资料 | 只保留背景，不作为当前实现依据 |

### 避免重复

- 业务规则在功能规格中写完整；产品设计只引用规则并描述交互。
- 页面状态在产品设计中写完整；模块 README 只记录代码边界和不可见的不变量。
- 契约字段以 OpenAPI／AI Schema 为准；文档使用示例时明确标注“示意”，不复制整份 Schema。
- 全局实现进度只维护在 [实现状态](./实现状态.md)；根 README 与 App README 仅给摘要和链接。
- 上线阻塞只维护在 [上线阻塞项](./TODO.md) 与相关边界文档；不在多个 README 复制同一清单。

### 变更时同步什么

| 变化 | 至少同步 |
|---|---|
| 业务行为、状态或验收变化 | 功能规格；涉及页面时同步产品设计 |
| API 字段、枚举、错误码或网络行为 | OpenAPI、生成产物、前后端、Fixture、测试；行为变化时同步功能文档 |
| AI Prompt、模型策略或结构化输出 | AI Schema／Prompt、运行时校验、Eval；用户行为变化时同步功能与设计文档 |
| 模块边界、数据流、事务或部署变化 | 整体架构设计及相关模块 README／部署说明 |
| 页面从原型接入正式数据，或正式能力退回占位 | 实现状态与对应模块 README |
| 权限、第三方处理、账号删除、公开页面或商店申报变化 | H5 与公开页面边界、上线阻塞项及对应功能／设计文档 |

修改完成后至少检查仓库内 Markdown 相对链接、旧名称与旧状态引用，并运行 `git diff --check`。代码或契约同时变化时仍需遵守根 `AGENTS.md` 的完整检查门禁。
