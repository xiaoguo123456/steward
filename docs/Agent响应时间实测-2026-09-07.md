## 瓶颈与改进优先级

### 1. 先减少无效重试，保证“有结果”

拆分存在偶发参数拒绝后仍未恢复的情况。当前 Runtime 给模型的 Schema 错误只是一条通用提示，没有具体字段路径。建议返回不含用户值的字段路径、错误类型及必填／类型约束，并区分已完成回复与未完成请求的评测指标。不要放宽 Schema、来源或确认门禁来换取通过率；修改后应重复运行拆分 Eval 和真实样本，观察成功率及额外模型往返。

这是可靠性与响应时间共同的问题，优先于单纯追求更早首字。后续独立的 7 类真实模型验收全部通过，也不能抵消本次已观察到的失败。

### 2. SSE 完成后立即刷新权威结果

`apps/mobile/src/app/ai.tsx` 中 Operation 每 900 毫秒轮询，`useTurnStream` 虽然记录 `finished`，页面并未据此刷新 Operation；建议卡片要等轮询发现终态后才重读。

建议在收到明确的 `done` 事件后立即重新读取 Operation，再读取消息和建议；连接错误仍交给原有恢复机制。当前 `finished` 同时代表 done、连接关闭与错误，不能不加区分就把它当成业务成功。可消除约 0–900 毫秒轮询等待，实际收益应通过同一原生路径 A/B 测量；不需要改模型或网络契约。

### 3. 减少串行模型往返

24 个正式 Assistant 样本中，Provider 路径累计耗时占 Worker 总耗时约 **99.3%**。排队为 2–94 毫秒；单个工具为 0–24 毫秒；Worker 扣除 Provider 后只剩 7–93 毫秒。因此当前低负载瓶颈主要在模型往返。Provider 计时包含网络和本地流式回调，不等于纯推理时间。

额外对 7 类请求单独运行计时版真实验收，确认了具体往返次数：

- 普通查询为 2 次，创建任务／日程通常 2 次。
- 修改、拆分均为 4 次：搜索 → 读目标 → 生成建议 → 最终说明。
- 修改最后一次说明耗时 1.16 秒，拆分最后一次说明耗时 1.82 秒。可评估在建议经过完整校验并持久化后，用确定性短说明直接结束这类简单轮次，或先展示有效卡片；必须保留用户确认和复杂多步骤请求的完整执行。
- 已在任务详情页发起的请求可优先利用正式 EntryContext 定位对象，仍在服务端按用户读取版本与来源；可少一次搜索，但不能省去权限、版本或来源验证。

以上是本轮轨迹支持的优化候选，并非已经实施的性能收益。每次调用约 3900–4400 输入 token，4 次往返累计约 1.6 万；按已确定场景缩减工具清单与上下文也值得评测，但不能让模型自行扩大授权，不能缓存用户业务结果跨用户复用。

### 4. 混合媒体采用有界并行识别

`captures/preprocess.go` 逐个识别图片、语音，再统一解析。混合样本中视觉为 0.80–1.95 秒，转写为 0.47–0.52 秒，两者串行。

对相互独立的媒体项采用受控并发，理论上可将识别部分由两者之和降到较慢者附近；这组图＋音样本约有 0.5 秒空间，更多媒体可能更明显。需要保留 Part 顺序、用户隔离、取消、失败门禁、Provider 限流及最终统一解析，不能让部分失败静默进入确认。该收益尚未做改造前后 A/B。

### 5. 补齐线上阶段指标，再考虑更换模型或扩大 Worker

Assistant 目前只持久化整轮 Provider 用量；视觉／语音预处理的审计模型字段为空，时延仍有记录，但按模型聚合会缺失归属。建议补充模型往返次数、每次耗时、修复次数、首字、队列和客户端展示时间，保持不记录正文或凭据。

Worker 的 AI 队列当前并发为 4；本轮串行采样没有证明它不足。不要依据这些低负载数据直接增大并发、关闭校验或重写编排框架。更换模型应比较成功率、来源质量、成本与尾延迟，不能只比较单次最快响应。
