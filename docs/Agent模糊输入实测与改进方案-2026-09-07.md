# Agent 模糊输入实测与改进方案（2026-09-07）

## 结论

优先修正“什么时候能生成建议”和“对话说法是否与真实建议状态一致”，再优化速度。当前对乱码、标点、简单缺失信息的处理总体正常；关键问题在同名消歧、日期推断、条件、取消和多轮补充。现有确认门禁仍然必要，但不能把错误建议的辨认责任全部交给用户。

本轮新增验收样本、真实模型探针、HTTP 补测和本报告，**没有实施下列产品或运行时修复**。

## 范围与方法

- 应用代码基于 `c3d0c53`，使用本地隔离 PostgreSQL 与真实 `qwen3.8-flash`，思考关闭。没有使用生产账号数据、真实用户资料或脚本模型代替理解能力。
- 正式数据包含 37 个场景，每个重复 2 次，共 84 次消息观测：4 次空输入拒绝、64 次 Assistant 应用服务调用、16 次 Capture 解析器调用。5 个场景含连续两轮，同一个场景内保留真实历史和待确认建议。
- Assistant 经过真实工具、来源、建议存储与任务状态检查，但直接调用应用服务，不包含 HTTP／River 排队。Capture 的 16 条单独解析结果不是 App 端到端结果，因此另外补测了真实 HTTP → Worker → 澄清 → 回答推进。
- 自动检查标记 15/84 条观测需要改善，分布在 9 个场景。这是定向边界样本的验收结果，不能当作线上失败率；未标记的回复仍需人工评审，不能等同于语义全部正确。
- 所有 64 条受理的 Assistant 样本，正式任务新增和更新计数均为 0；测试没有确认任何建议。每个虚构用户结束后自动删除。HTTP 测试 Capture 已废弃，临时登录文件收尾删除。
- 前一次探索运行发现测试收集器原本面向单轮，会把旧建议计入本轮；已按 Turn ID 过滤。时间冲突题也改为明确互斥表述，避免混淆“截止”与“计划时间”。随后完整重跑，本报告的 84 条均来自修订后的同一轮正式运行，未拼接挑选最快或最好的结果。

## 观察到的问题

| 场景 | 正式观察 | 判断与处理方向 |
|---|---|---|
| 两个完全同名的“周报” | 1 次用完 4 次模型往返后泛化降级；1 次明知有两条仍任选一条生成改期建议 | 不唯一时立即展示可区分的候选，等待用户选择，不能继续猜 |
| “过几天提醒我交材料” | 1/2 次擅自填成 9 月 11 日，并在降级回答时仍保留建议 | 模糊日期保持未定；需要实际提醒时间时问具体日期 |
| 同时要求改截止又保持当前截止不变 | 1/2 次一边承认冲突，一边生成修改建议 | 未解决的互斥要求必须阻断可执行建议 |
| “已完成才改期，否则不要动”且实际未完成 | 1/2 次仍生成改期建议 | 条件结构化，Go 读取并验证，不成立就不生成修改 |
| “2 月 30 号交周报” | 1/2 次擅自顺延为 **2027 年 3 月 2 日** | 日期格式合法不代表忠实原意；非法日期不能自行顺延 |
| “明天下午评审”→“三点到四点” | 第一轮 1/2 次擅自设置 14:00–15:00；第二轮 2/2 次没有生成新的正确建议 | 关键时间必须先澄清；补齐后不得重复询问可选信息或让用户手动修旧错误建议 |
| 已有买牛奶建议后说“算了” | 2/2 次旧建议仍 pending，回复却说“作废了” | 取消必须执行正式拒绝操作，回复由真实结果生成 |
| 撤回长期偏好、说明只是今天想跑步 | 2/2 次旧长期记忆建议仍 pending | 当前意图应废弃旧建议，不能只改聊天说法 |
| Capture 中说“不记任务，只是随口说想买牛奶” | 2/2 次转成“想买牛奶”笔记候选；HTTP 也复现 | 需要明确“随口说”的产品语义，不能默认把不记任务转换成记笔记 |

“补充具体时间”两次失败原因不同：一次模型只能看到还有一条 pending，无法读取旧建议内容，要求用户自行确认或取消；另一次已经有标题和时间，却继续追问评审对象、地点或链接，把可选字段当成阻塞项。

还观察到：长期偏好撤回后的解释曾把当天说成“周三 9 月 9 日”，而测试日期是 9 月 7 日。没有生成日期字段，因此未进入上述字段断言计数，但说明自然语言说明也需要可靠的时间来源。

### 能正常处理的部分

- 空字符串和普通纯空白均被拒绝；HTTP 返回 `400 / VALIDATION_FAILED`。
- 乱码、纯标点、纯数字、表情、无上下文“好的”、宽泛指令和无目标“那个”，这轮均没有生成建议，也没有调用工具。该组 16 条受理样本响应约 0.60–2.63 秒，中位数约 1.08 秒。
- 纯不可见格式字符仍会进入模型，约 1 秒后得到提示。可在判空时改善，但不要改写有效正文里的连接符或表情序列。
- “买牛奶”可直接得到不带截止日期的任务建议；正式复测中的“帮我记个任务”→“买牛奶”也正常接续。不能因为句子短就拦截。
- 显式否定、只讨论假设、同句改口、临时状态和澄清中切换话题，当前这两次采样均未生成错误建议。样本很小，不代表所有复杂否定都可靠。
- Capture 对乱码、缺少指代能生成阻塞问题；对模糊日期能保留无日期任务；对矛盾／冲突时间能保留警告与问题。

### HTTP 补测与否定边界

- 乱码：`awaiting_instruction`，零候选、一个阻塞问题；回答“记录买牛奶、不设日期”后 revision 推进，进入 `needs_confirmation`，有 Task，未再追问。零候选的确认请求被参数校验拒绝，不能据此声称验证了 Domain 状态门禁。
- 开会 10:00 开始、09:00 结束：`awaiting_instruction`，一个 Event 候选和阻塞问题。使用真实候选提前确认得到 **CAPTURE_NOT_READY**；回答正确时间 10:00–11:00 后 revision 推进，进入 `needs_confirmation`，无遗留问题。这验证了真正的状态门禁和恢复。
- “不要记任务，只是随口说”会产生 Note；而更明确的“不要保存成任务、笔记或任何记录”补测得到**零候选**。因此不能笼统说 Capture 忽略所有否定。这里按“不应把随口说默认保存为其他类型”的产品预期标记需改进。
- 明确不保存时虽是零候选，Capture 仍标为 `needs_confirmation`，没有阻塞问题。App 会显示无可保存内容的空态，但这个业务状态命名仍值得改进，不能让用户误以为还需要确认。

## 建议的输入处理规则

以下为待实现／待产品确认的目标行为，保持原生对话、卡片和确认流程；不新增 H5 或第三方 Provider。

| 输入 | 推荐反应 | 允许的动作 |
|---|---|---|
| 空白或全部不可见格式字符 | 输入框不发送，服务端同样拒绝 | 不调用模型 |
| 无上下文乱码、编号或标点 | 简短说明缺少什么，例如“你想记录还是查询什么？” | 无目标时不查私有数据、不生成候选 |
| 表情、寒暄、只讨论假设 | 自然简短回应 | 不推导任务或长期偏好 |
| “把那个改到明天”或同名对象 | 有上下文就用可验证引用；否则给最少的候选选项 | 用户消歧前不能生成目标修改 |
| “买牛奶” | 展示无日期任务建议 | 可选日期、备注、地点不阻塞 |
| “过几天”“下午”或不存在的日期 | 保留未定字段，必要时问一个关键问题 | 不擅定星期、小时，不顺延非法日期 |
| 关键条件不成立、明确否定或互斥要求 | 说明未操作，或询问哪项要求为准 | 不生成具有确定字段的错误建议 |
| 当前建议后说“算了” | 唯一当前目标可直接拒绝该建议；有多个目标先消歧 | 仅改变待确认建议状态，不自动删除已保存内容 |
| 追问后的补充 | 合并到当前问题，已有信息不再问 | 更新同一待确认意图的版本，旧版本失效 |
| 用户换话题或表示不想补充 | 结束当前追问，保留可返回入口 | 不反复催问，不擅自补齐 |

不要建立“少于几个字就是无意义”的规则，也不要全局删除数字、标点或 Emoji。“3”在选项里、“好的”在上下文中都可能有效。确认正式写入仍由既有原生确认路径完成，不能把随口的“好的”当作越过确认门禁的授权。

## 实施顺序

### 第一批：建议正确性与状态一致性

1. **补齐当前意图和建议上下文。** `assistant/context.go` 目前只告诉模型“有 N 条待确认建议”，没有提供对应 ID、类型、版本、最小预览和当前澄清字段。增加有用户隔离的最小上下文与正式读取能力，关联正在讨论的对象，解决“看不到上一张卡片”和重复建建议。
2. **让取消与修订形成真实状态变化。** 通过正式 Application／Domain Command 拒绝或 supersede 指定 Proposal，返回新版本；旧卡片立即失效。唯一目标可以处理，有多个时先问。不要让模型直接写库，也不要因取消一条待确认建议而删除已经保存的任务。
3. **把关键条件和消歧结果变成结构化前置条件。** 例如目标必须唯一／已经由用户选定、任务状态必须为完成。Go 在生成建议和确认时分别核对。首版只支持能明确表达和验证的条件，不能解析的复杂条件先澄清，不承诺任意自然语言都可自动执行。
4. **使用字段级来源与确定性时间解析。** 当前来源校验保证引用存在，却不能保证日期能从引用推出。让模型提交原始时间表达及来源位置，由 Go 解析支持的明确表达；模糊或非法表达返回 unresolved，不能提交模型自选的日期。任何“建议时段”必须明确标为建议，不能冒充用户给定的截止时间。
5. **区分对话结果。** 将有效回答、需要澄清、建议已就绪、已取消和降级分开；“已生成／已作废”的提示必须根据持久化后的真实结果生成。正常澄清没有 Proposal 是成功，用户已补齐信息却没有 Proposal 则不是请求完成。不要只看 Operation succeeded。
6. **区分用户控制语句和待整理素材。** 用户直接输入的取消／不要保存属于操作意图；图片文字或引用材料中的类似句子仍是资料，不能触发取消或外部操作。针对“随口说”明确两条入口的一致规则，不默认降格成 Note。

相关改动必须同批完成行为文档、需要变更的 OpenAPI／生成 Client、AI Schema、服务端状态、原生卡片、Fixture 和回归；只改 Prompt 不能完成以上状态与执行约束。

### 第二批：在正确结果上提速

- 将上述必须澄清、否定、不猜日期的例子加入 Prompt 和真实 Eval，可以先减少犯错；Prompt 不能替代服务端前置校验。
- Schema 拒绝时返回安全的字段路径、约束类型与缺失字段，不回传用户值或底层异常；让模型有依据纠错。不要靠不断增加重试次数或放宽 Schema 提升“成功率”。
- 同名或缺目标一旦识别，立即展示选项，避免继续查日历、记忆和重复对象直到耗尽 4 轮。本轮同名样本花了约 4.3–5.1 秒却没有可靠解决问题。
- SSE 的明确 done 事件触发权威结果刷新，保留断线恢复，减少原有最多约 900 毫秒轮询等待。不能把连接关闭或错误当作成功。
- 简单建议经完整校验并持久化后，用确定性短状态说明结束或先展示有效卡片，减少最后一次模型往返；修改与拆分此前最后说明约花 1.2–1.8 秒。复杂多步骤请求另保留完整执行。
- 图片与语音的独立预处理采用有界并发，保留顺序、取消、失败门禁与限流；本组一图一音的理论节约约半秒。以上提速仍需改造前后 A/B，当前未实施。

## 如何验收改进

- 固定本轮 37 个场景，增加独立改写、错别字、方言式表达与带上下文的短回答；不要只为固定原句写关键词补丁。
- 自动门槛分别统计：不恰当建议、擅定日期、错误目标、条件违背、虚假完成说法、取消后仍 pending、补齐后重复追问、未确认正式写入。保留真实失败样本，不把“被门禁拦住了”一律记成理解成功。
- 继续人工审查澄清是否具体、选项是否有依据、是否错误透露工具／内部字段，以及最终回复中的日期是否正确。
- 每个改进至少做多轮独立复测，并增加新措辞留出集；要评估线上比例需更大且有代表性的样本，本轮 2 次重复不足以估计真实发生率。
- 性能同时报告“有效建议／有效澄清”到达时间与成功率。无结果的快速回复不能算提速；目标是减少无用模型往返，保留必要的用户选择。

## 复现与证据

正式样本定义：`packages/ai-contracts/evals/ambiguity-live.json`。

在配置了专用隔离数据库与真实 Provider 的工作树运行：

```sh
STEWARD_AI_LIVE_AMBIGUITY=1 go -C apps/backend test -count=1 -timeout=12m -v ./internal/platform/ai/eval -run '^TestLiveAmbiguityAcceptance$'
```

测试默认跳过真实调用；显式启用时当前**会失败**，因为它保留了上述质量问题。常规 `make check` 通过不代表这些真实模型问题已修复。

HTTP 补测入口为 `tools/agent-latency/ambiguity-http.ts`，沿用该目录 README 的本地登录、打包与输出环境变量；可用 `STEWARD_AMBIGUITY_HTTP_CASE=明确不保存` 单独补测强否定。脚本只使用正式生成 Client，清理时废弃本次 Capture，不确认正式内容。
