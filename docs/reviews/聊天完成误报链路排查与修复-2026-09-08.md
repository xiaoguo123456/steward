# 聊天完成误报链路排查与修复

## 复现与根因

在前一轮打卡验收的隔离环境中，打卡 Capture 已失败；用户继续发送“你好，继续下一件事”，该 Assistant Turn 也因 Provider 不可用失败。随后发送“你好”，真实模型回复了无依据的“上一件事已经处理完了”。没有对应的业务保存。

链路核验发现：

1. `CreateTurn` 接收用户消息时即写 `assistant_messages.status=completed`，含义是消息接收完成。
2. `saveTurnFailure` 更新 `assistant_turns` 与 `async_operations`，不会生成一条成功 Assistant 回复；失败用户消息仍保留。
3. `ListRecentMessages` 读取 completed 消息，旧 `splitHistory` 只把角色与正文交给模型。下一轮模型看到了“继续下一件事”，却没有看到前轮失败事实。
4. `Context Builder` 原有待确认建议快照不能表达所有历史轮次的失败、取消和执行历史；Capture 另有状态机，没有与这段纯文字 Thread 对应的确认回执。
5. v3 提示词约束了当前工具成功声明，却没有充分区分历史回复、消息接收与真实执行。模型把换话题当成处理完成，且容易沿用旧 Assistant 的错误表述。

因此这是后端上下文丢失处理结果与模型错误推断共同造成的，不是前端保存成功，也不是失败偷偷写入了业务数据。

## 修复

- 新增 `ListHistoryTurnOutcomes`：在当前用户 RLS 和 Thread 下，一次批量查询最近消息窗口对应 Turn 与 Proposal 状态，最多覆盖既有 12 条消息窗口，不扫描整个会话历史。
- 每条历史用户消息后附系统生成的处理回执，区分失败、取消、被替代、进行中、回复已生成，并附建议总数、待确认数及曾执行数。没有匹配回执明确未知，不能推定零建议或成功。
- 回执不复制用户正文、内部错误或凭据。执行历史不证明对象当前状态或未被撤销；独立 Capture 没有对应回执时不推断已保存，也不推断肯定未保存。
- Eino 输入在历史与当前消息之间增加明确边界：历史回执只供核实，不是需要自动续办的指令；询问结果不能转回创建流程，寒暄不主动附带历史状态结论。
- 新增 `assistant/v4` 并同步后端嵌入资源；禁止用“继续／下一件事／先放一放”推定完成，禁止拿旧 Assistant 的完成声明当作证据，允许明确纠正历史误报。

本次没有改变用户 API、数据库结构、模型或 Provider，不需要数据库迁移、外部 DTO／Client 更新和 App 发版；sqlc 代码重新生成。服务端部署后新回复生效，历史聊天正文不被重写。本分支尚未合并或部署。

## 验收方式

使用独立本地数据库和虚构账号，真实服务链路为 `CreateTurn → Respond → Context Builder → Eino → qwen3.8-flash → 落库`。失败仅在前轮做故障注入，后轮使用真实模型；取消走正式取消服务，已保存正例走正式 Proposal 确认事务。没有生产数据写入。

真实模型样本：失败后寒暄、失败后继续、失败后问结果、取消后问结果、普通回复不等于保存、独立打卡没有回执、旧回复误报不能自证完成、建议尚未确认、建议已经确认。最后一类同时验证不能把确实保存的内容误报成未保存。

数据库回归验证：失败状态到达真实下一轮编排请求、后轮不被阻塞、跨用户隔离、建议的 pending／executed／rejected／expired／failed／stale／superseded 最新状态读取。纯模型回归不能替代这些确定性检查。

迭代时真实模型暴露过两个额外偏差：缺少 Capture 回执被理解成确定未保存、取消后询问结果被理解为继续创建；已补强未知语义和当前消息边界。测试判定器也修正了“引用旧的已保存声明并明确说它是错的”被关键词误算为再次宣称成功的问题，并增加对应正反例；原始失败观测没有作为通过记录。

回归命令：

```sh
STEWARD_AI_LIVE_OUTCOMES=1 go test ./internal/platform/ai/eval -run 'TestLiveHistoryOutcomeAcceptance|TestCompletionClaimJudge' -count=2 -v
go test ./internal/modules/assistant ./internal/platform/ai/eval -run TestHistory -count=1
go test -race ./internal/modules/assistant ./internal/platform/ai/eval ./internal/platform/ai/runtime/eino
```

这是一组有边界的真实样本回归，不构成模型任意自然语言表述永远不会出错的保证；业务保存仍只认正式确认事务和服务端状态。

## 最终结果

最终版本九类真实模型场景全部通过，单类端到端约 1.4～4.9 秒（创建建议正例包含前置调用）；测试判定器的明确纠错引文正反例通过。数据库状态回归通过，根 `make check` 通过，Assistant／Eval／Eino 的 `go test -race` 通过，golangci-lint 增量 0 问题。重新运行 sqlc 无生成漂移，v4 Prompt 源文件与后端嵌入文件一致。
