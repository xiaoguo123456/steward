# 体重记录卡住排查与修复

## 生产证据

2026-09-08 按用户授权对尾号 3360 的生产账号只读排查，并以 `app.user_id` 限定 RLS 身份，未修改或确认用户数据。用户明确输入体重数值与公斤单位后，首轮错误建议绑定专注的时长字段，并询问是否创建“体重追踪器”。两轮解析分别耗时约 3.54 秒、3.32 秒，Operation 均已 succeeded；第二轮 Capture 为 needs_confirmation。

第二轮候选中 Tracker 的 fields 为 null，Record 没有 tracker_ref，残留 tracker_id 与 tracker_ref 缺失标记。它们只是未确认候选，没有写入正式体重或专注记录。本文不复制用户体重数值、完整手机号或原始对话。

## 根因

1. 旧 AI Schema 没有 tracker_fields 和同批 tracker_ref 的表达通路，Provider 中立类型及映射也未实现；构造 Tracker payload 时只填名称，序列化出了 null 字段。
2. Capture 保存未预分配同批 Tracker 引用；Record 不能连接新 Tracker。
3. 移动端正式 Zod 校验拒绝该响应，但 Query 缓存仍停在 parsing。Operation 已成功时，阶段判断忽略带旧缓存的 Capture 错误，持续显示“正在整理可确认的结果”。
4. 新记录项编辑器直接请求尚未存在的候选 ID，造成额外的读取失败；默认摘要还会显示“未命名内容／1 个字段”。

## 修复

- Capture Prompt v7、Schema v5 增加完整记录字段与同批引用。清楚的首次记录请求直接生成关联候选，一次确认保存；缺少数值先询问，避免“追踪器”等术语。
- 解析落库前验证字段、唯一引用、目标类型和 Record key。全批预分配 candidate_id，支持前向依赖；确认仍由原有领域事务先创建 Tracker 再保存 Record。
- 删除 Tracker Command 缺少字段时擅自补出默认 value 字段的兜底；缺少字段必须明确拒绝。
- 无上下文的纯文字裸数字在模型成功响应后经过保守澄清门禁，不能被猜测成记录。该门禁不代替模型、不处理 Provider 故障兜底。
- 旧空字段快照可读为可恢复失败，保留数据库原始输入与快照，不伪造字段。读取失败时 App 退出转圈并显示重新加载。
- 确认卡片显示记录名称、数值、单位；同批编辑直接使用待确认字段；未选关联新记录项时阻止保存并提示一起选择。

公开 OpenAPI 字段与数据库结构未变，复用现有 CaptureDraftPayload、TrackerField、RecordValue 和错误码，因此无需 Goose 迁移或重新生成不变的 HTTP DTO／Client。AI 资产从权威 packages/ai-contracts 同步；新增跨端 Fixture 与正式生成 Zod 校验测试。

- 正式数据库确认测试：确认前无 Tracker／Record，确认后仅一条正确关联的体重记录；重复确认重放同一 Activity Batch。
